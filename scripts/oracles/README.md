# The oracles

Probes over a corpus of the shapes that have gone wrong before. All but one run every rule of the plugin against every primary option it accepts; `pairs.ts` runs every pair of those instead. Each asks a question no test case in this repository can ask, and the table below is the list of them — a count of them written into this prose would fall behind the next one written.

```shell
make oracles                        # measures what is not kept, then writes tmp/oracles-diff.md
make oracles BASE=<rev> HEAD=<rev>  # any two revisions; the defaults are where the branch left origin/main, and the working tree
```

The two sides are compared rather than written: every result is kept under `~/.cache/stylelint-stylistic/` by what it depends on — the hash of the `lib/` tree it was measured over, of the scripts and the corpus that measured it, and of the lock file — so a base is measured once for every branch that stands on it, an amended or rebased commit whose `lib/` did not move keeps its result, and a run only ever measures the side no entry answers for. A directory of scripts stands in that key as the hash of its sources rather than the one Git keeps of its tree, since a test or a document standing beside a script is not something a result depends on and rewording either would otherwise send all six to measure both sides afresh. `make cache-gc` takes out what no branch, remote or tag still reaches. A run of the six takes about twenty seconds, and each writes JSON: a list of rows, one per rule, option, syntax and fixture that answered wrongly — or, in `pairs.ts`, one per pair of configurations and fixture. `compare.ts` runs them one at a time with the working tree's scripts over either side's `lib/`, which `HARNESS_LIB` names, so that the two sides are always asked one question; every script writes to standard output.

| Oracle | Asks |
| --- | --- |
| `converge.ts` | Does `--fix` reach a fixed point, and does what it wrote still parse? |
| `control.ts` | Does a `//` comment move a warning, against a block comment of exactly the same width? |
| `comments.ts` | Does every comment the file held survive the fix? |
| `twins.ts` | Does a rule say the same thing about a file broken with a Windows pair as about its line-feed twin, and does the syntax read the twin at all? |
| `nodes.ts` | Does every declaration, rule and at-rule the file held survive the fix? |
| `pairs.ts` | Does `--fix` leave a different file behind when the configuration lists two rules the other way round? |

`twins.ts` and `nodes.ts` were written on 2026-08-22, after three branches in a row turned up bugs the first three could not see. Their first numbers are a census rather than a backlog: 372 rows of `twins.ts` belong to a rule and 4 to none at all, and they are one bug wearing many faces, which [#250](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/250) counts. A twin is reported once, on the first disagreement it shows, so the number is a lower bound rather than a tally.

`pairs.ts` was written on 2026-08-26, when a rule that writes a solidus and a rule that would space one were about to join a class nobody had counted. Its first numbers are a census too: 215 rows, 61 of them `hard`, over 74 distinct pairs of rules, which [#356](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/356) sorts into four classes and [#352](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/352) to [#355](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/355) hold. Until those close, read this one by the pairs a branch adds or removes rather than by the pile it stands on.

## What to do with them

**The diff is the finding, not the count.** `tmp/oracles-diff.md` holds it, row by row:

- a row the branch **adds** is a defect the branch introduced. File it from the branch that made it, rather than leaving it for the next review;
- a row the branch **removes** goes in the pull request body;
- a row that was there before and is there after belongs to an open issue, and the issue is where it is answered;
- a row that was there before and merely became **reachable** is none of those three. It belongs to the census it came from, and the branch says so in its pull request body instead of opening an issue of its own. Four issues were opened from one branch on 2026-08-22 for want of this line, and three of them were things a sweep turned up rather than rows that branch added.

None of them has to come back empty before anything can land. What they buy is that the size of the backlog is known, and that no fix quietly grows it.

Seven issues came out of the first run of them, [#231](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/231) to [#237](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/237). None had been filed, and none had been found by a review.

## Why a test case cannot ask any of this

`testRule` asserts `fixed` — the output of **one** run of the fixer, against one input. So:

- it never runs the fixer twice, which is what `converge.ts` is for;
- it never compares two spellings of one file, which is what `control.ts` and `twins.ts` are for;
- it asserts the whole output, so a deleted comment is caught only where somebody thought to write a case with a comment in it, which is what `comments.ts` is for, and code swallowed into a comment that survives is caught by nobody at all, which is what `nodes.ts` is for;
- it lints under one configuration, spelled one way round. A case naming a second rule through `extraRules` asserts the order it happened to write them in, and never the other, which is what `pairs.ts` is for.

An oracle is worth what it can be shown to catch, and a probe that has never been seen to fire says nothing about the code. `nodes.ts` reported nothing when it was written, because no fixture stood where a fixer takes a break away from an inline comment; `inline-after-brace` and `inline-after-semicolon` were written with it, and it then reported [#248](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/248) four times over. `grid-empty-row` was written the same way for [#368](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/368), a row of the grid holding no cell at all, which no fixture carried: `converge.ts` reports that shape three times over the code as it stood before that fix — once per syntax — and comes back clean from the fix itself.

## The runner

None of them calls `stylelint.lint`. A call of it over a snippet costs about 0.8 ms, and 0.7 of them are the linter around the rule — a linter created for the call, a configuration searched for and augmented, an ignore file looked up, reference roots loaded, disable comments walked — while the parse and the rule cost 0.05 ms together; over the 350 000 calls a run of the six makes, that is the difference between five minutes and twenty seconds. So [scripts/harness/lint.ts](../harness/lint.ts) does what `lintPostcssResult.mjs` does for one rule and nothing of the rest, and answers in the shape the oracles read. `make harness-check` is the proof that the two agree: every run the oracles make, checked and fixed, and every fixture under pairs of rules in both orders, compared with Stylelint field by field. What the runner does not reproduce — disable comments, `ignoreDisables`, `quiet`, `computeEditInfo` — no fixture carries, and a rule reaching for one of them would show up there as a disagreement.

The same runner drives the sweeps of [scripts/sweeps/](../sweeps/): a sweep is a module exporting a corpus, most often built by multiplying axes with [scripts/harness/matrix.ts](../harness/matrix.ts), and the configurations to read it under; `make sweep FILE=scripts/sweeps/<name>.ts [BASE=<rev>]` lints it on the base and on the working tree in one process — the base's `lib/` is extracted under `tmp/checkouts/` by the hash of its tree, so the working tree is never moved for a run — and writes the rows that moved to `tmp/sweeps/<name>.md`, row by row and never by count. A sweep is kept once it has measured a branch, the way a fixture is kept once it has caught a defect.

## The files

`runs.ts` builds the list of runs every oracle makes — every rule, under every primary option, over every fixture — and each oracle is one loop over that list. `fixtures.ts` and `options.ts` are what it reads.

`fixtures.ts` holds the shapes the convergence, comment, twin and node runs read. `control.ts` carries its own, since every fixture there has to be written so that both spellings of its comment give the same code, and `pairs.ts` carries its own as well, since what it needs of a shape is that many rules have something to say about it at once. `twins.ts` writes every break of a fixture back as a line feed before respelling it, since respelling directly would turn an existing `\r\n` into two breaks and ask the rule about a file that is not the original's twin at all — and skipping such a fixture instead would drop the only shapes in the corpus that carry whitespace in front of a break, which is what [#247](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/247) turns on. Two of the shapes of `pairs.ts` end on something other than a line break, since every fixture ending on one leaves the fix of `no-missing-end-of-source-newline` unreachable and a whole class of [#356](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/356) unseen.

The corpora are short on purpose — a row that fires on twenty fixtures says no more than one that fires on one, and every fixture costs the run about a dozen lints per rule and option, or, in `pairs.ts`, the square of the rules it wakes. **Add a shape when a defect is found that the corpus did not catch**, and the oracle catches it the next time.

`options.ts` lists every rule and its primary options, written out rather than read off the source, so that a run over an older commit compares with a run over a newer one. A rule gaining an option gains a line here in the same commit. Options taking a number or a shape rather than a keyword are given one or two representative values, and a rule whose secondary options change its behaviour is not covered at all — `ignore`, `ignoreFunctions`, `except` and the rest are all unexplored ground.

## What they cannot see

- No fixture reaches `at-rule-semicolon-space-before`, which [#139](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/139) names among the rules whose warnings an inline comment moves. The drift is real; the fixture for it is not written yet.
- `control.ts` compares warnings and not outputs. A rule that correctly declines to write into a comment differs from its block-comment twin on purpose, so comparing the two outputs reports every guarded rule as a finding. Whoever wants the output half of that comparison has to tell the two apart first.
- **A fix that is wrong but tidy passes every one of them.** [#230](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/230) rewrites a Less calculation into two values and [#234](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/234) spells `!important` in capitals; both converge, both keep every comment, both leave every node standing, and neither turns on how a comment or a break is spelled. The corpus carries `group-with-unit`, `nested-group` and `two-bangs` for them all the same, so that a later fix cannot make either shape worse without a row appearing — but finding such a defect in the first place still takes a reader. [#366](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/366) is a third of the kind: a call nested in another was written a second time over the code standing behind the outer one, and the value that leaves re-parses, holds every comment and every node, and does not move on the run after, so `converge.ts`, `comments.ts` and `nodes.ts` all came back clean over `nested-func-empty-lines` on the checkout that wrote it, and the rows `twins.ts` puts on that fixture turn on how a break is spelled rather than on the duplication. That fixture is carried for the same reason the other three are. [#298](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/298) is a fourth: a unit written in front of an interpolation holding whitespace came back from `--fix` with the name inside that interpolation recased, and what leaves re-parses, holds every comment and every node, and stands still on the run after. `interpolation-with-space` is carried for it on the same footing as the other four, and is written as a custom property, since a declaration's value is where the issue stands and a custom property is how all three syntaxes carry one.
- **A warning that is wrong passes every one of them too.** None of the six asks what a warning says about the file it was raised over. Each compares one run with another — a fix with a second fix over its own output, a `//` comment with the block comment standing in its place, one spelling of a break with another, a file with what the fix left of it, one order of two rules with the other — and a name that is wrong is wrong alike on both sides of every one of those. So [#297](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/297) named `PX*2REM*3EM` a unit, drew two warnings over one `PX` and drew none at all over the `REM` and the `EM` behind it, and every run came back clean. The corpus carries `multiplied-units` for the shape all the same, on the same footing as the five above: it guards what a later fix writes there and where it says it, not what it calls a unit. `slash-star-slash` and `nested-group` reach that branch of the rule already — they hand it the words `*a`, `b*` and `*` — but `getDimension` reads no number in any of the three, so no part of them was ever measured as a dimension.
- **`comments.ts` counts openings, and the corruption of [#272](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/272) keeps the count.** A comment opening `/*/` comes back out of `postcss-value-parser` as `/**/`, which turns one comment into a comment and three characters of code — but the `*` written in gives the text behind it an opening of its own, so `x/*/*a,b*/` and `x/**/*a,b*/` both tally two. The `slash-star-slash` fixture has stood in the corpus since #238 and three of the runs over it rewrote the value that way, and the oracle came back clean from all three. Only three: that fixture carries no media query, no hex colour and no unit, so it never reaches `media-feature-parentheses-space-inside`, `color-hex-case` or `unit-case` at all, and those three of the five rules #272 is the census of are unmeasured rather than measured clean. Counting is what buys this oracle its cheapness, and telling the widening apart wants the openings placed rather than tallied. [#370](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/370) is the same widening in `function-max-empty-lines`, and `slash-star-slash-empty-lines` was written for it — where the count is kept for a reason of its own rather than the one above: `/*/x*/` and `/**/x*/` each hold a single `/*`, so the star written in opens nothing. The corrupted value re-parses, keeps every node and does not move on the run after, so five of the six oracles come back clean over that fixture on the checkout that wrote the fix; the sixth is `twins.ts`, and what it says about it turns on how a break is spelled rather than on the widening. It is carried against a later fix rather than for that one.
- **`twins.ts` sees only what the corpus holds.** `no-empty-first-line` wants an empty first line, which no fixture carries: it comes back clean from the run and wrong from a probe written for it by hand, it is measured in the census of [#250](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/250), and the fixture for it is not written yet. `addEmptyLineAfter` is reached and does write — one `--fix` over every run the corpus makes calls it 42 times — but never down the one branch of it this oracle would have something to say about: the line feed `getLineBreak` falls back on where the configuration lists no `linebreaks` and the file spells no break of its own, which a stylesheet asks for only by ending no line at all. No fixture ends that way. Two rules have left this list, and for opposite reasons. `named-grid-areas-alignment` wants a *mis*aligned grid, which the `grid` fixture is not; `grid-empty-row` gave it one, and under that the twin run reports nothing about it. `max-empty-lines` wants an empty line, which nothing here carried until `nested-func-empty-lines` was written for [#366](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/366), and under that it reports six rows. That one shape reaches `function-max-empty-lines` and `value-list-max-empty-lines` as well, neither of which any other fixture wakes, while `max-line-length` and `no-multiple-whitespaces` report on it alongside twelve and six other shapes of their own. The five of them put 45 rows on the board between them, and the rule as it stood before #366 was fixed puts the same 45 there: they are the census's rows rather than that fix's. `slash-star-slash-empty-lines`, written for [#370](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/370), wakes the same five and adds 39 rows more, and those 39 stand alike on either side of that fix as well.
- **`pairs.ts` reads its corpus as CSS, two rules at a time, under primary options alone.** A pair that races only over a shape the corpus does not hold, only under a custom syntax, only through a secondary option, or only in company of a third rule, is unmeasured rather than measured clean. Its count is a lower bound like the twins' one.
- **`pairs.ts` pairs only the rules that rewrite a fixture on their own.** A rule that changes nothing there cannot race with another over it, which is what buys the run its cheapness — but where one of the two only becomes able to write once the other has written, the pair is never made at all. The `max-empty-lines` half of [#390](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/390) is exactly that, and stays unmeasured on a checkout where it stands.
- **`pairs.ts` calls a pair contradictory by the file the fixer rests on, and it tells resting from taking turns only since 2026-09-01.** It used to read a pair by one pass of the fixer and drop it where both orders left warnings behind — which is what a contradicting pair does when it rests, and what it does just as well when two rules take one character in turns, each pass writing a diff and no pass the last. [#416](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/416) measured thirty-one such pairings by a probe of its own, and the one such pair this corpus held was dropped. The fixer is now run pass after pass until it writes a file it wrote before, and a pair one of whose orders never does is a `cycle` row, kept whatever the warnings say; the `hard` and `soft` rows are still read off the first pass, so that the census keeps its rows. What the filter above lets through of the class is little: only the pairs of two rules that each rewrite the fixture alone are made, and in most cycling pairs one of the two is content with the fixture as written — so `whitespace-value` puts one row of #416 on the board, the one cycling pair both of whose rules rewrite it alone, where the branch closing it measured sixty over eleven shapes and forty-five pairs of configurations by a probe of its own. The row is a guard against the class coming back rather than a census of it.
- **`pairs.ts` compares the file a run leaves and not the warnings it printed.** Where the order moves a column rather than a character it says nothing, and that is the fifth shape of the class, the one [#356](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/356) records in a comment rather than in an issue of its own: every position this plugin reports is measured while the tree is still being written, so a neighbour listed ahead moves it. The half of that class the oracle sees is the half a fix writes.
