# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com), and this project adheres to [Semantic Versioning](https://semver.org).

## [Unreleased]

### Changed

- The plugin now reads a line break the way PostCSS does: a line feed, with or without the carriage return of a Windows pair in front of it, and nothing else. A bare carriage return and a form feed are whitespace to every rule, as they are to PostCSS's line counter — a rule reading a line in either reported a position the file does not have, since Stylelint counts lines by PostCSS. Every rule about a break, an empty line, an inline comment's end or a multi-line list is affected: a file broken with bare carriage returns or form feeds is one line to all of them now. The `linebreaks` rule tells `\n` from `\r\n` and leaves a bare carriage return where it stands.
- Every rule that writes a line break now writes the one the `linebreaks` rule asks for, wherever the configuration lists that rule, and otherwise the one the file spells its lines with (see [#352](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/352)). Stylelint runs each rule once and in the order the configuration lists them, so a break another rule wrote behind `linebreaks` used to stay a line feed in a file of Windows pairs until the next run of `--fix`; there is no order the two disagree in any more. A file that ends no line at all is given a line feed, never the line ending of the machine.
- False negatives are fixed — a violation the plugin used to pass over in silence, whether `--fix` was asked for or not, is now reported:
	- The `color-hex-case`, `function-comma-*`, `number-*` and `unit-case` rules now read a call whose name a hexadecimal escape welds to the word in front of it (see [#344](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/344)). CSS closes such an escape with one whitespace character belonging to the escape rather than to the text, so `a { b: \61 url(13PX); }` names one call, `aurl`, which `lightningcss` compiles to `a { b: aurl(13px); }`, lowercasing that unit itself, and Sass to `a { b: aurl(13PX); }` — an ordinary call to both, whose arguments are the author's. `postcss-value-parser` reads no escape and hands that call back named `url` alone, which is what these rules matched against, so everything such a call held was passed over as an address's. The name is gathered back together now, and what stands inside is read like any other value. The other half of this reading, where an address written with an escape stops being rewritten, is under `Fixed` below.
	- The `selector-descendant-combinator-no-non-space` rule now reads a selector whose comment the parser carries across a parenthesised group (see [#159](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/159)). A group standing where a combinator belongs is nothing `postcss-selector-parser` has a place for: it reads the group as a combinator whose value is the whitespace in front of it and the group itself, and files a comment standing between the two behind that node rather than inside it, so `.foo /*c*/\t( )\t.bar` came back out of the parser as `.foo ( )/*c*/\t\t.bar` — the comment across the group, and a tab where none was written. The rule passed such a selector over, and a list at a time, so a run standing in a neighbouring selector went unreported with it. The node is given its own text back now, so the group is reported where it stands and the whitespace behind it is collapsed like any other descendant combinator's, the comment keeping the place the file gives it. Only a comment with a space in front of it was ever read that way, however wide the whitespace is: that space is what the value of such a combinator opens with, while a comment standing behind a tab or a line break the parser already prints as the file spells it.
	- The `selector-descendant-combinator-no-non-space` rule now reads a selector carrying an inline comment under `postcss-scss` (see [#158](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/158)). That syntax rewrites such a comment into a block comment in the copy the rule reads, keeps the source spelling in the copy it prints, and the two drift apart by two characters per comment, so the rule used to pass the whole selector list over. Every position is now translated back into the file's own coordinates, and a fix is written to both copies with the comments spelled the way the file spells them. The whitespace standing behind an inline comment is passed over on its own: the line break in it is what closes the comment, so a single space could not be written there, and asking for one would leave a warning no run of `--fix` could clear.
	- The `selector-pseudo-class-parentheses-space-inside` rule now reads a selector carrying an inline comment under `postcss-scss` (see [#163](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/163)). It used to pass such a selector over, as [#161](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/161) left it: the two copies that syntax keeps of a selector drift apart by two characters per comment, so a position counted in the copy the rule reads points past the character it is about, and a fix written there never reaches the file. Both are answered now, so the pseudo-classes of such a selector are spaced out like any other. Where the whitespace in front of the closing parenthesis is the line break that closes an inline comment, that end is passed over instead: a space written there would take the parenthesis into the comment, and taking the break away would do the same.
	- The `selector-pseudo-class-parentheses-space-inside` rule now reports the whitespace standing in front of a closing parenthesis where a comment closes the arguments (see [#128](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/128)). The parser kept none of it, so the `never` options passed `a:not( /**/ )` over while reporting the same space in `a:not( b /**/ )`; both are now read alike.
	- The `declaration-colon-space-after` rule now looks for the whitespace after the colon where a custom property whose value holds a comment actually keeps it (see [#109](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/109)) ([@VChet](https://github.com/VChet)):
		- the `always` options no longer report `--a: /*comment*/ !important;`, whose single space is already in place, and no longer pass over `--a:/*comment*/ !important;`, which has none at all;
		- their fix no longer adds a space of its own on every run, so two spaces or a tab after the colon now become the single space asked for;
		- the `never` option now takes the whitespace away instead of reporting a fix and leaving the declaration as it was, and no longer reports one that has no whitespace to begin with;
		- a space or a tab standing in front of the colon is no longer counted as one standing after it.
	- The `declaration-colon-*-after` rules now look for the whitespace behind the colon where a declaration whose value holds no word of its own actually keeps it (see [#371](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/371)). PostCSS hands that whitespace to `raws.between` only where the value has a word to leave behind; where all that stands behind the colon is whitespace, comments and a flag, `raws.between` ends at the colon and the run stays at the head of the value instead — in the raw of it where PostCSS keeps one, and in the value itself where it does not. Only the guard [#109](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/109) above left behind ever looked there, and only for a custom property. The declaration is read now down to the end of its value, as the file prints it, and the run is moved to where PostCSS itself keeps it whenever a value has a word before anything is written over it, so `a { color:  !important; }` and `a { color: /*comment*/\t!important; }` are answered like any other declaration:
		- the `always` and `always-single-line` options of `declaration-colon-space-after` no longer report a declaration whose single space is already in place, and their fix no longer writes a space of its own beside the run rather than over it, which used to grow the declaration by a space on every run;
		- the text those options count the lines of is that declaration's own value now, where it used to be the text around it: the value of `a { color\n:  !important; }` is empty, and an empty text stands on one line, so `always-single-line` speaks about that declaration as it always has about `a { color\n:  pink; }`, and `always-multi-line` of `declaration-colon-newline-after` is silent about it as it always has been about the twin;
		- its `never` option now reports such a run and takes it away, instead of passing the declaration over in silence;
		- `declaration-colon-newline-after` no longer reports a declaration whose break already stands where the option asks for it, and no longer writes a line break of its own on every run under either of its options;
		- the break that rule writes now goes behind a comment standing on the colon's own line rather than in front of it, as it always has where the value has a word, so the position such a problem is reported at moves to the end of that comment.
	- The `declaration-colon-space-before` and `declaration-colon-space-after` rules now work on the declaration's own colon instead of the first colon they come across (see [#92](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/92)). A comment standing in front of the colon may hold a colon of its own, an URL for one, and used to be taken for the declaration's:
		- the fix no longer edits the text of such a comment;
		- the `never` options no longer miss the real violation hiding behind it;
		- the `always` options no longer report a declaration that is already correct.
	- The `declaration-block-semicolon-newline-after`, `declaration-block-semicolon-newline-before`, `declaration-block-semicolon-space-after` and `declaration-block-semicolon-space-before` rules now check the declarations of an inline `style` attribute (see [#49](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/49)). A page gives such an attribute a root of its own with no rule inside it, and the four rules used to pass over every declaration whose parent is not a rule, so nothing was reported for `style="color: pink;top: 0;"` in an HTML, Vue, Svelte or Astro file, while the `<style>` block of the same page was checked as usual. The top level of a Sass file is left alone as before, since a variable written there is not a declaration block.
	- The `selector-descendant-combinator-no-non-space` rule now reports a parenthesised group standing after a space where a combinator belongs, `.foo (  ) .bar` for one (see [#125](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/125)). The rule used to read a combinator only where its value was a single space, so every such selector went past unseen; a group holding one space or none, `.foo ( ) .bar` and `.foo () .bar`, is reported alongside the rest. Nothing can be written to repair such a selector, so the problem is reported and the code left exactly as it was.
	- The `selector-descendant-combinator-no-non-space` rule no longer turns itself off for a selector carrying a comment (see [#124](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/124)). One comment anywhere in a selector list used to silence the rule for the whole list, so a violation standing in a neighbouring selector went unreported along with it:
		- a descendant combinator holding comments is now measured run by run, each stretch of whitespace reported at its own position and collapsed on its own, so that every comment stays where the author put it;
		- the whitespace after a comment that follows a combinator of another kind, `.foo > /*comment*/  .bar` for one, is passed over, since there is no descendant combinator there to measure;
		- an illegal combinator carrying a comment, `.foo /*comment*/ (  ) .bar` for one, is reported as [#125](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/125) has it, and left exactly as it was.
		- a selector carrying an inline comment is read as well, which was [#158](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/158) and is answered below.
		- a selector the parser does not give back as it took it is passed over too, which is [#159](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/159): a comment standing in front of a parenthesised group is filed behind it, and nothing the rule could say about such a selector would match the file.
	- The `indentation` rule now measures the lines a comment used to hide from it (see [#194](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/194)). A selector line holding nothing but a block comment was blank in the copy the rule read and passed over in silence, and is brought to its level now, in a plain CSS file as under `postcss-scss`. A pair of literal slashes in a plain CSS selector — text to CSS, which has no comment of that kind — used to swallow the line break behind it whole, so the lines after it went unmeasured too, and are measured now. And a line that was already at its level behind a comment is no longer reported at a drifted position, so a false warning goes with the false silences.
	- The `indentation` rule now measures the lines standing behind an inline comment in a declaration's value or in an at-rule's parameters (see [#236](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/236)). The search that finds the line breaks of such a text read the break closing an inline comment as part of that comment and never handed its position over, so every line after it went unmeasured: the second line of `a { b: 1px // c` drew nothing at all, where the same file spelled with a block comment of exactly that width was reported and brought to its level. That search is handed a copy with the comments blanked out of it now, the one the rules reading a value for a comma or a bang are already handed, so a value, the arguments of a function inside it and an at-rule's parameters are all measured whichever way their comments are spelled, under `postcss-scss` and `postcss-less` alike. A line of a selector holding nothing but an inline comment is measured too, which it had not been since [#194](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/194) left such a line blank in the copy the scan reads: every line is measured in the text the file spells instead, so `a,` followed by a line carrying only `// c` is brought to the level of the list like any other. In a value and in a set of parameters such a line was measured all along, and still is. And a double slash the file spells no comment with no longer hides the lines behind it, in a selector and in a set of parameters as in a value: `a { b: url(http://x/y.png)` followed by a mis-indented line is reported like any other, `@import url(http://x/y.css)` followed by one is too, and a plain CSS selector carrying such a pair no longer has the line break behind it swallowed along with the pair. The scan is told which syntax spelled the text now, so a double slash is read as a comment only where one is spelled that way — and the `*/` closing one block comment beside the `/*` opening the next is no longer read as a pair at all, so `a { b: 1px/*x*//*y*/` followed by a mis-indented line is reported as well.
	- The `indentation` rule now reports every mis-indented line of an at-rule's parameters holding comments, at the line and column the file spells (see [#65](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/65)). The lines were sought in a copy of the parameters with the comments taken out: a line holding nothing but a comment was blank there and passed over in silence, and the warning that did appear was placed by an offset into that shorter text, at `1:30` where the file has `2:3`. The scan reads the copy the file spells now and the fix writes to it, so both mis-indented lines of the issue's `@use './button' with ( … )` are reported, each asking for the `1 tab` it needs, and every comment survives the fix that used to strip all three.
	- The `value-list-comma-*`, `media-query-list-comma-*` and `function-comma-*` rules now report a comma standing behind an address (see [#153](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/153)). The search that finds the commas of a value and of a media query list read the double slash of `url(http://x/y.png)` as the opening of an inline comment, so everything from there to the end of the line was comment text to it. In a value that took the closing parenthesis of the address with it, and the count of open parentheses never came back down, so every comma that followed — on the address's line and on every line after it — stood inside a function's arguments as far as the search was concerned, where it passes them over; a media query list is read without skipping a function's arguments, so there it was the commas on the address's own line that were lost. The four `function-comma-*` rules read the same double slash the same way, through a pattern of their own, and said nothing about the comma of `image-set(url(//cdn/a.png) 1x ,url(//cdn/b.png) 2x)`. All twelve are told which double slash opens a comment and which only looks like one now, so `a { b: url(http://x/y.png),'z'; }` is reported like any other value list, and fixed by the ten of them that fix anything. Nothing about this needs a comment anywhere, or any syntax but plain CSS: an address on its own was enough.
	- The `declaration-bang-space-*`, `media-feature-colon-space-*` and `media-feature-range-operator-space-*` rules now read what stands behind an address (see [#215](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/215)). The search these rules place their matches with reads a double slash as the opening of an inline comment wherever it stands, the one in `url(http://x)` among them, and everything from there to the end of the line was comment text to it, so `a { b: url(http://x)!important; }` drew nothing from either bang rule and the second feature of `@media (min-width: url(http://x)) and (max-width:1px)` drew nothing from any of the other four. They are told which double slash opens a comment and which only looks like one now, as [#153](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/153) told the comma rules; nothing about this needs a comment anywhere, or any syntax but plain CSS.
	- The `value-list-comma-*`, `media-query-list-comma-*`, `function-comma-*`, `declaration-bang-space-*`, `media-feature-colon-space-*` and `media-feature-range-operator-space-*` rules now read three double slashes the file does not spell a comment with (see [#216](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/216)). The search these rules place their matches with was handed a copy in which every double slash that opens no comment is written over, and three of them could not be: the `*/` closing one block comment and the `/*` opening the next spell a pair between them, and neither slash can be written over without taking a comment away, so `1px/*x*//*y*/,2px` drew nothing; a pair whose second slash opens a block comment was held back for the same reason, though the one in `url(a//*b*/)` opens nothing, so `url(a//*b*/),2px` drew nothing either; and a pair standing in plain CSS, which spells no comment that way at all, was read as one, so `myurl(//a),2px`, `image-url(//a),2px` and `a//b,2px` drew nothing either. The comments are blanked out of the copy now, delimiters and all, so no reader is left to find them for itself, and a double slash is taken for a comment only where the syntax spells one — which plain CSS does not, and `postcss-scss` and `postcss-less` do.
	- The `function-whitespace-after` rule now reads what stands behind an address (see [#225](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/225)). It places its matches with the same search the rules above do, and was left on the old reading of it, so the closing parenthesis of `a { b: myurl(//a)red; }` drew nothing. It is handed the copy the others are handed now. The blindness was never plain CSS's alone: the search reads the double slash of `url(http://x)` as opening a comment whatever the file is written in, so `@import url(http://x)screen;` drew nothing under `postcss-scss` and `postcss-less` either, and the parenthesis in front of `screen` is reported now whichever of the three the file is.
	- The `media-feature-parentheses-space-inside` rule now reads a media feature standing behind a double slash the file spells no comment with (see [#225](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/225)). It finds the comments of the parameters for itself, to keep `postcss-value-parser` out of their text, and read a double slash as opening one whatever syntax had spelled them, so everything behind `myurl(//a)` was comment text to it and neither space of the second feature of `@media (myurl(//a)) and ( min-width:1px )` was reported. That scan is told which syntax spelled the parameters now, as the searches above are. An address was never the trouble here: the scan told the double slash of `url(http://x)` from a comment all along.
	- Every `*-multi-line` option now counts a form feed as the line break it is (see [#244](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/244)). `isSingleLineString` — which `whitespaceChecker` asks for every one of those options, and which `block-closing-brace-empty-line-before`, `block-closing-brace-newline-before`, `function-parentheses-newline-inside` and `function-parentheses-space-inside` ask directly — read a line feed and a carriage return and nothing else, so a construct broken with a form feed alone passed for a single line and every multi-line option passed it over in silence: `a {color: pink;\ftop: 0;}` drew nothing from `block-opening-brace-newline-after`, `a { b: fn(1,\f2); }` nothing from `function-parentheses-newline-inside`. Thirty-five rules ask that question, and all of them read the three characters every syntax this plugin reads through ends a line on now, as [#173](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/173), [#196](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/196), [#204](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/204) and [#209](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/209) each taught one reading before them. Two rules were left half repaired by that change, each because a second reading of its own counted line feeds alone, and each already wrong that way for a bare carriage return: `block-closing-brace-empty-line-before` read an empty line as two line feeds, which is [#245](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/245), and `function-parentheses-newline-inside` asked whether the break it wants is already standing by looking for a line feed, which is [#246](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/246). Both are answered below.
	- The `no-eol-whitespace` rule now sees the whitespace at the end of a line a form feed ends (see [#247](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/247)). The scan that finds where the lines end read a line feed and a carriage return and nothing else, so the space in `a { color: pink; \f}` was reported by none of the rule's options and left standing by `--fix`, while the same stylesheet spelled with any of the other three breaks was reported at `1:17` and came back trimmed. The three characters every syntax this plugin reads through ends a line on are read now, in the text of a comment as in the CSS around it, at the end of the file, and where `ignore: ["empty-lines"]` measures a line for emptiness. The warning keeps the position postcss gives it, which counts a form feed as no line at all, so a file broken with one draws every one of its warnings on line 1 — a reading of the file that happens before any rule of this plugin and is not one it can put right.
	- The `function-whitespace-after` rule now reads a call whose name closes on a digit or an underscore where no other call is open around it (see [#230](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/230)). The search the rule used to place its matches with read a parenthesis as a call's only where an ASCII letter stood in front of it, and let every parenthesis standing inside a call's arguments past whatever named it, so `a { b: atan2(1,2)red; }`, `a { b: a_(1)red; }` and `@import col-6(a)screen;` drew nothing while the same three calls nested inside another were reported all along. The rule looks for the calls of the text now, rather than coming across the parentheses of it. The `never` half of an escaped parenthesis is read now too: `a { b: url(a\)b) red; }` drew nothing, the search having placed the address's closing parenthesis two characters early, and the space behind the address is closed up like any other.

The name was read back from the parenthesis as a run of letters, digits, underscores and hyphens, and an identifier is wider than that in three directions and is not a run of characters at all: it may hold code points outside ASCII, it may close on a hyphen, it may open on anything behind a leading `--`, and an escape spells one of its characters with several. Such a query used to be reported and then left exactly as it was, the warning disappearing with the fix, so the problem survived any number of runs.
	- The `selector-pseudo-class-parentheses-space-inside` rule now fixes the whitespace next to a closing parenthesis that a comment stands in front of (see [#123](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/123)). The parser keeps such a comment, and the space on either side of it, in the raws of the node before it, and prints the raw one; the rule wrote to the clean value instead, so the problem was reported, `--fix` claimed a clean pass and the parenthesis stayed exactly where it was. A nested pseudo-class was left half fixed at every level. Under `always` a line break in front of the closing parenthesis now collapses to a single space where a comment stands before it, as it already did where none does.
	- The `value-list-comma-space-after`, `value-list-comma-space-before` and `value-list-comma-newline-after` rules no longer drop the warning about a comma they cannot fix (see [#126](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/126)). A comma the value does not hold is out of their reach, and they said so by returning `false` from the fixer — a refusal Stylelint has never read, since it counts a fixer as applied whatever it does. So `--fix` ended with a clean pass on a file it had not finished fixing, and only a second run over the output brought the surviving problem back. A warning of that kind now stands where it used to vanish. A comma opening the value was among them at the time, and is fixed by all three rules now, which was [#134](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/134) for two of them and [#166](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/166) for the third.
	- The `no-eol-whitespace` rule now trims the end of a Less file whose last line is an inline comment closed by a bare carriage return (see [#247](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/247)). `postcss-less` ends such a comment on a line feed and on nothing else, so where the file ends on a carriage return that break stays in the raw behind the comment's text, with the whitespace in front of it; only the very end of that raw was trimmed, and the break stands there, so `// c  \r` and `a { b: 1; } // c  \r` were reported while `--fix` came back with a clean pass on a file it had not touched. The lines of that raw are walked now, and the same file ending on a form feed — which said nothing at all until the widened scan above reached it — is trimmed alongside. A Less file ending on a line feed was never affected: that break closes the comment, and the whitespace in front of it is the stylesheet's own to trim.
	- The `no-eol-whitespace` rule now trims an inline comment that holds nothing but whitespace (see [#254](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/254)). Such a comment is filed as an empty text with every character of the whitespace in the raw in front of it and nothing in the raw behind, and only the raw behind was trimmed at its end, so a line holding `//  ` and nothing else was reported while `--fix` came back with a clean pass on a file it had not touched, and the warning went with it. The end of an inline comment is taken to be the end of whichever raw closes it now, so such a line comes back as `//` and a second run has nothing to say. Under `postcss-scss` that holds wherever the comment stands and whichever of the four spellings of the break closes it, the end of the file included. Under `postcss-less`, which files that whitespace elsewhere wherever a line feed closes the comment, it holds for a file that ends inside one: whatever spaces and tabs such a comment ends on are trimmed now, however many bare carriage returns or form feeds stand in front of them, while the whitespace in front of each of those breaks was trimmed already — in front of a bare carriage return by the walk over the lines of that same raw, and in front of a form feed since [#247](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/247) taught the scan to read one as the end of a line. A comment that holds text keeps the single space between the slashes and that text, which ends no line, and a block comment holding nothing but whitespace, `/*  */`, is untouched as before, its whitespace standing in front of the closing delimiter rather than at the end of a line.
	- The `linebreaks` rule now rewrites a line break standing in a set of at-rule parameters (see [#270](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/270)). The warning came from a scan of the file itself, which sees every break whichever text of whichever node it stands in, while the fix walked the tree and wrote to a selector, a value, the text of a comment and the whitespace around a node — a set of parameters being none of those, and the one at-rule the fix did reach being a Less at-variable, which `postcss-less` gives a value beside its params. So `@media (min-width: 1px),` broken with a line feed under `windows` was reported at `1:25`, `--fix` reported a clean pass, the file came back byte for byte as it went in, and a second run reported `1:25` again. The parameters of every at-rule are read and written now, in the copy the file spells, so a comment they hold survives the fix.
	- The `linebreaks` rule now rewrites a line break standing in four more of the texts a node holds (see [#283](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/283)). The warning comes from a scan of the file itself, which sees every break whichever text of whichever node it stands in, while the fix walked the tree and wrote to a selector, a value, a set of at-rule parameters, the text of a comment and the whitespace in front of a node and at the end of its block. Four texts were none of those: what an at-rule writes between its name and its parameters, what a rule, an at-rule or a declaration writes between its two halves, the raw of a `!important`, and the whitespace inside the delimiters of a comment. So a stylesheet broken over `a` and `{ b: c; }` was reported at `1:2` under `windows`, `--fix` reported a clean pass, the file came back byte for byte as it went in, and a second run reported `1:2` again. Seven shapes went that way: a break between the name of an at-rule and its parameters, between those parameters and the block, between a selector and its block, between a property and its value, between a value and the bang behind it, behind the opening delimiter of a comment, and in front of the closing one. All seven are rewritten now, and a colon standing in one of those four texts is left exactly where it is — the colon that parts a declaration, and the one `postcss-less` files behind the name of a Less at-variable — breaks being all the fix reads. One shape of this is still open: a break in front of a stray semicolon standing behind a nested block goes the same way, and is [#372](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/372).
	- The `function-parentheses-newline-inside` rule no longer reports a problem solved that it could only half write (see [#285](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/285)). The walk that measures the whitespace behind an opening parenthesis steps over the nodes an inline comment is spelled with, and the `never-multi-line` fix stops at the first of them, so what the fix could not reach stayed and the option stayed violated: `a { t: translate( // c` followed by a line break, ` /*x*/`, a line break and ` , 1px); }` came out of `--fix` with the space behind the parenthesis taken and the line break left, and `stylelint` reported on the very file `stylelint --fix` had just called clean. The fix is written now only where it empties every stretch that was measured, and the problem is reported where it is not.
	- The `declaration-block-trailing-semicolon` rule no longer reports a Sass nested property solved and leaves it exactly as it was (see [#335](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/335)). Such a property is a declaration carrying a block, which `postcss-scss` alone reads as one — every other syntax reads `font: 12px { … }` as a rule — and the fix of this rule writes no character itself: it sets the block's `raws.semicolon` and leaves the printing to the stringifier, which drops the semicolon it is handed for a declaration carrying a block exactly as PostCSS drops it for an at-rule carrying one. So `a { font: 12px { family: serif; } }` under `always` was reported, called fixed and written back byte for byte, the warning gone with the run. The at-rule walk of the rule turns such a node away already; the fix is now declined for the declaration too, so the warning survives `--fix` rather than vanishing with a write that never lands. Whether such a semicolon can be written at all is a question of its own, and where such a property already carries one behind its closing brace the warning is raised over a file that needs nothing — that semicolon is parsed into the block's own trailing raw rather than into the flag the rule reads, which is [#336](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/336) and older than either.
	- The three `block-closing-brace-*-before` rules now write the whitespace in front of a closing brace wherever the parser filed it (see [#292](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/292)). Where an at-rule carrying neither a block nor a semicolon of its own closes the block, that whitespace stands inside the at-rule, and all three rules wrote the block's own raw, which is empty there. So under `never`, `never-single-line` and `never-multi-line` nothing was written at all, and under `always`, `always-single-line` and `always-multi-line` the character went into the empty raw beside the whitespace it was about, satisfying nothing: `a {` followed by a break, `@extend .b` and a break came back from `block-closing-brace-space-before` one space longer on every run, for ever. Either way the warning vanished with the fix and the next run raised it again. One shape of that kind is left exactly as it was — a Less mixin call carrying `!important`, where `postcss-less` collects the whitespace on both sides of the flag into one raw and prints all of it on one side, so that neither raw describes the run in front of the brace ([#374](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/374)). Every other is written exactly like the same block ending in a declaration with no semicolon now, under every option of the three rules and under all three syntaxes, and a comment the at-rule swallowed along with the whitespace keeps its place. A fix that could only be written by taking the brace into an inline comment is still held back, and its warning still stands.

### Added

- The `max-line-length` rule now has an additional `tabSize` option (see [#10](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/10)). A tab used to count as one character, so a file indented with tabs measured shorter than the editor showed it; with the option a tab reaches the next tab stop of the given width, as the CSS `tab-size` property has it, and the limit is the one the editor's ruler shows.
- The plugin now says so when it is listed in `extends` instead of `plugins` (see [#14](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/14)). It is a plugin rather than a shareable config, and Stylelint could not tell the one use from the other: it loaded the package as a config, found no rules in it, and reported every `@stylistic/` rule of the config as unknown — an error about the rules, whose cause is the field they were never reached from. A run now stops with a configuration error naming the field to move the package to.
- The `aspect-ratio-notation` rule, which specifies how the value of `aspect-ratio` is written (see [#18](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/18)). One and the same ratio can be written in more than one way, and the rule reads a value along two axes that do not depend on each other: the primary option `"ratio"|"number-where-possible"|"as-written"` says how many of the two numbers are written, since the grammar reads `2` as `2 / 1`, and the optional `smallestIntegers` option says what those numbers are, since `16 / 8` spells the ratio `2 / 1` as well. Either axis can be given without the other, and both are settled before anything is written, so one run of `--fix` leaves the value as the configuration asks for it.
- The plugin now ships a type declaration for what it exports, so a TypeScript configuration or a script importing the package reads the plugin list as `Plugin[]` rather than as `any`. Nothing about configuring the plugin changes.

### Fixed

- The output no longer turns on the order the configuration lists two rules in — Stylelint runs each rule once, in the order its entries are spelled, and a plugin's rules stand nowhere in Stylelint's own registry, so that order is the user's:
	- The `no-missing-end-of-source-newline` rule now closes a file ending on a free semicolon the same way whichever side of `no-extra-semicolons` it is listed on (see [#390](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/390)). Everything standing behind the last block is parked in one raw of the root, and this rule's fix asked that raw alone whether the file had ended its last line — but `no-extra-semicolons`, listed first, has already taken the semicolon out of it, and what is left ends on the break the file spells in front of that semicolon. So `@media all { a {} }` followed by a line break and a semicolon came out of `--fix` closed by an empty line where this rule was listed first and by a single break where it was listed second, neither run reporting anything about the other's output. The raw and the file are both asked now, and the run of spaces the file ends on comes off only where the two agree it is there: the raw is the only place this fix can write, and the file is the text the warning was made about. Both orders leave the longer of the two files — the empty line where the semicolon stood — since this rule writes its break behind whatever the author put there and takes none of it away; how many empty lines a file may end on is `max-empty-lines`' to say, and the whitespace-only line a semicolon standing in a run of spaces leaves behind is `no-eol-whitespace`'s. Nothing about a file no neighbour has written into moves — over 960 runs of the rule on its own, fourteen bodies and thirty tails under `css`, `postcss-scss` and `postcss-less`, not one warning and not one output changed.
- A fix that could only be written by commenting the code out is now reported instead — an inline comment ends only with a line break, so the character an option asks for has nowhere to go:
	- The `function-parentheses-newline-inside` rule no longer takes the code behind a function's opening parenthesis into an inline comment standing in front of it (see [#129](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/129)). 	- The `media-query-list-comma-space-before` rule no longer takes a comma standing behind an inline comment onto that comment's line (see [#137](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/137)). The line break in front of the comma is what closes such a comment, so neither option can be satisfied without commenting out the rest of the query and the block behind it, and the problem is now reported rather than fixed.
	- The `value-list-comma-space-before` rule no longer takes a comma standing behind an inline comment onto that comment's line (see [#136](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/136)). The line break in front of the comma is what closes such a comment, so neither option can be satisfied without commenting out the rest of the declaration, and the problem is now reported rather than fixed.
	- The `function-comma-space-before`, `function-comma-space-after`, `function-comma-newline-before` and `function-comma-newline-after` rules no longer write into an inline comment standing in a function's arguments (see [#135](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/135)):
		- a comma standing behind such a comment is no longer taken onto its line, since the line break in front of the comma is what closes the comment, so the problem is now reported rather than fixed;
		- a comma standing inside the text of such a comment is no longer taken for a comma of the value at all, so nothing is reported for it and nothing written near it.
	- The `declaration-colon-space-before` rule no longer rewrites a declaration whose property is followed by an inline comment into code that does not parse (see [#88](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/88)). Such a comment ends only with a line break, so neither option can be satisfied without taking the colon into the comment, and the problem is now reported rather than fixed.
	- The `block-opening-brace-newline-before` rule no longer takes the opening brace into an inline comment standing in front of it (see [#89](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/89)). Such a comment ends only with a line break, so the `never-*` options cannot be satisfied without commenting the whole block out, and the problem is now reported rather than fixed.
	- The `declaration-bang-space-before` rule no longer takes `!important` into an inline comment standing in front of it (see [#116](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/116)). Such a comment ends only with a line break, so neither option can be satisfied without commenting out the flag and the semicolon behind it, and the problem is now reported rather than fixed. A double slash belonging to an address, or standing inside a string, opens no comment of that kind, so a flag written on the line under a value that ends in `url(http://example.com/a.png)` is still pulled up to it.
	- The `declaration-block-semicolon-space-before` rule no longer takes the semicolon into an inline comment standing in front of it (see [#117](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/117)). An `!important` that `postcss-less` reads out of the text of such a comment, where Less reads comment text and nothing else, no longer hides the comment from the rule either (see [#211](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/211)): `color: red // c !important` comes back from that parser as a value of `red // c` with the flag set, and the value and the raw of the flag are asked together now, since the write follows both. That holds where the semicolon already stands on the comment's line as well, `color: red // c !important;`, which the parser keeps no raw of at all.
	- The `declaration-block-semicolon-newline-before` rule no longer takes the semicolon into an inline comment standing in front of it (see [#207](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/207)). The `never-multi-line` option trimmed every trailing whitespace of the value, or of `!important` where the declaration carries it, and the line break closing such a comment went with the rest, so `color: red // keep me` followed by `;` on the next line came out of `--fix` as `color: red // keep me;`, the semicolon commented out and the declaration ending nowhere, with nothing reported. An inline comment ends only with a line break, so the option cannot be satisfied without commenting the semicolon out, and the problem is now reported rather than fixed; a block comment, an address and a string holding a double slash are still fixed; an `!important` that `postcss-less` reads out of the text of such a comment, where Less reads comment text, does not hide the comment from the rule; and the `always` options never were in that danger, since the break they write is what closes such a comment anyway.
	- The `declaration-block-trailing-semicolon` rule no longer writes the semicolon into an inline comment (see [#232](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/232)). The guard it carried asked about one raw of one node — the one standing where a bodiless at-rule's closing brace would be — so it held under `postcss-scss`, which keeps such a comment in that raw, and nowhere else. `postcss-less` keeps a comment behind a value inside the value and one behind an at-rule's parameters inside the parameters, so `color: pink // keep me` closing a block came out of `--fix` as `color: pink // keep me;`, the semicolon commented out and the block ending nowhere, with nothing reported, and `@include x // keep me` went the same way. Whichever text the node the semicolon is written behind ends with is asked now, the value and the raw of `!important` together where that node is a declaration, so an `!important` that `postcss-less` reads out of the text of such a comment does not hide it either; an inline comment ends only with a line break, so the `always` option cannot be satisfied without commenting the semicolon out, and the problem is now reported rather than fixed. An address and a string holding a double slash are still fixed, plain CSS spells no comment with a double slash at all, and the `never` option never was in that danger, since it takes a semicolon away rather than writing one. A block comment standing behind a bodiless at-rule is still fixed as well, and so is one standing behind the value of a custom property, which every syntax keeps inside that value; behind the value of an ordinary declaration such a comment never reached this rule at all, since it is read as a node of its own and the declaration is then not the last of its block. A custom property written on a single line is held back for the same reason as everything else: nothing closes the comment in front of the brace, so the semicolon would stand inside it. One broken across two lines is not: both syntaxes read such a value to the end of the line and take the line break into it, so the semicolon lands past the comment rather than inside it, which is [#287](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/287).

Such a comment ends only with a line break, so `never-multi-line` cannot be satisfied without commenting out the parenthesis, and everything the declaration has left, and the problem is now reported rather than fixed. The `always` and `always-multi-line` options add a line break rather than take one away, and are unaffected.
	- The `function-parentheses-space-inside` rule no longer takes a function's closing parenthesis into an inline comment standing in front of it (see [#114](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/114)). Such a comment ends only with a line break, so no option can be satisfied without commenting out the parenthesis, and everything the declaration has left, and the problem is now reported rather than fixed. All four options are asked, the guard belonging to the fix rather than to any one of them. A value with no comment in it is fixed exactly as before.
	- The `function-parentheses-space-inside` rule no longer takes the code behind a function's opening parenthesis into an inline comment standing in front of it (see [#280](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/280)). The line break in that whitespace is what closes such a comment, so no option can be satisfied without commenting out the first argument, and everything the declaration has behind it, and the problem is now reported rather than fixed — which is what the closing parenthesis has done since [#114](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/114), and what the sibling rule's opening parenthesis has done since [#129](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/129). All four options are asked, and each of them under the reading the file's own language has, which [#333](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/333) settled for every guard of the family: a fix that language is not at risk from goes through as before, and so does every fix of a value with no comment in it.
	- The `block-opening-brace-newline-after` and `declaration-block-semicolon-newline-after` rules no longer take the code behind an inline comment into that comment (see [#248](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/248)). The line break their `never-multi-line` option takes away is the one that closes such a comment, so whatever stood behind it — a declaration, a nested rule, a whole at-rule and its block — went into the comment's text, and out of the stylesheet altogether: what the fixer wrote parsed perfectly well and the next run had nothing to say about it, though the block had lost everything it opened with and nothing anywhere said so. The problem is now reported rather than fixed. The whole run of comments a block opens with is asked about rather than the last of them alone, since that option takes every break in front of the first node away at once, and a block comment standing between an inline one and that node used to be carried into the inline comment along with it. Where the comment is one `postcss-less` reads an `!important` out of the text of, the flag is asked about with it as [#211](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/211) had it; and where a value ends in the break that closes its own comment, the semicolon standing behind that break is asked about too, so a fix that would comment nothing out is written as before. The `always` options were never in this danger and are untouched, since the break they keep or write is what closes such a comment anyway. In `declaration-block-semicolon-newline-after` a comment a form feed closes is held back with the rest, which is [#295](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/295): Sass ends a comment on that character and Less does not, and the shared guard reads only the breaks the two of them agree on.
	- The `block-closing-brace-space-before` and `block-closing-brace-newline-before` rules no longer take a block's closing brace into an inline comment standing in front of it (see [#231](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/231)). The whitespace between the last node of a block and its brace is what these fixes write over, and the line break in it is what closes such a comment, so every option of the first rule and the `never-multi-line` option of the second commented the brace out along with everything the block had left: `a {` followed by `color: pink // c` on a line of its own came back from `--fix` as a file with no closing brace at all, which neither Sass nor Less reads, however happily `postcss-less` parses its own output. The problem is now reported rather than fixed. A break the fix leaves standing is the one exception. Neither rule reaches the whitespace the last node of the block ends with, so a break standing there closes the comment whichever of the two is asked; and the first writes over only the whitespace ending the block's own final raw, so a break in front of a stray semicolon of that raw survives it as well, where the `never-multi-line` fix of the second takes every whitespace of the raw away. Wherever such a break stands, the brace lands outside the comment and the fix runs exactly as before. The `always` options of the second rule were never in this danger, since the break they write is what closes such a comment anyway, and a block whose brace a comment had already swallowed is put right by them.
	- The `function-parentheses-newline-inside` rule no longer takes a function's closing parenthesis into an inline comment with two fixes that are safe apart (see [#312](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/312)). The `never-multi-line` option writes two of them in one pass over one value — one emptying the whitespace behind the opening parenthesis, one the whitespace in front of the closing one — and each was weighed against a value that still held the other one's whitespace. Where a call holds nothing but comments there is no first argument to ask about, so both questions are about that same closing parenthesis, and the break either fix leaves behind was the one keeping it out of the comment: `a { t: 1px // c` followed by a form feed, `calc(`, a line break, `/*b*/`, a line break and `); }` under `postcss-scss` came back as `a { t: 1px // c` and a form feed and `calc(/*b*/); }` on a run that reported nothing at all, the parenthesis and the semicolon and the closing brace all inside the comment under the reading Less has. The two fixes are weighed together now, over the union of what either of them empties, and neither is written where that union carries a character into a comment: both problems are reported and nothing goes into the file. A fix that is not safe on its own is still never written, and the other is then weighed as the only fix there is, so nothing is held back that was never at risk. That stylesheet is fixed under `postcss-scss` since [#333](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/333) gave the guard the reading Sass has — the form feed closes the comment, and there is nothing for the parenthesis to fall into — and left alone under `postcss-less`, where the whole of `calc(` stands inside the comment and the rule reads no call there at all. No syntax this plugin is tested under reaches that weighing any longer, and it is kept for a custom one that names neither reading, where both are owed.

	- The `declaration-block-trailing-semicolon` rule no longer takes away the semicolon Less asks for behind an at-rule carrying no block of its own (see [#309](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/309)). Nothing about it turned on the at-rule's name or on a comment: `@import`, `@layer`, `@supports` and an at-rule Less has never heard of went the same way, whether they closed the block on their own or stood behind a declaration. A Less variable declaration is a third such shape, and the semicolon behind one is now left standing too: telling it from an at-rule means reading its value the way Less reads it, and Less asks that the whole of that value parse as an expression of its own, `a { @v: pink !IMPORTANT }` and `a { @v: a:b }` being `@v rule is missing block or ending semi-colon` as readily as `a { @extend .b }`. So `a { @v: pink; }` under `never` is reported rather than fixed now, where it used to be fixed and rightly, and that is the price of the guard. A declaration Less reads no value in loses no fix and still breaks: that is [#358](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/358).

	- The `linebreaks` rule no longer drops the comments a value holds when it rewrites the line breaks of a file (see [#235](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/235)). It rewrote every value it walked, and the copy it rewrote was the one PostCSS hands back with the comments taken out, so a value spanning lines lost them all — `a { b: 1px /* c */` and `2px; }` on the line under it came out of `--fix` under `windows` with the comment gone. The break is now written into the copy the file spells, comments and all, and the breaks a comment itself holds are rewritten with the rest, since a break standing inside a comment is a break of the file like any other.
	- The `linebreaks` rule no longer drops the comments a selector holds when it rewrites the line breaks of a file (see [#269](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/269)). This is [#235](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/235) one property over: the fix wrote `rule.selector`, the copy PostCSS hands back with every comment taken out, and PostCSS threw the raw those comments live in away along with the copy `postcss-scss` prints, so `a /* c */,` broken with a line feed over `b { c: d; }` came out of `--fix` under `windows` as `a ,` and the comment was gone, with nothing reported. A comment written with a double slash went the same way under `postcss-scss`. The selector is read and written in the copy the file spells now, so every comment survives the fix, in plain CSS and under both custom syntaxes. A selector holding no line break was never affected, and by accident: the fix hands such a selector back unchanged, so the bare copy still matched the raw and PostCSS went on printing the raw.
	- The `number-*` rules no longer drop the comments a value or a set of at-rule parameters holds when they add or take away a zero (see [#268](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/268)). These rules read `decl.value` and `atRule.params`, the copies PostCSS hands back with every comment taken out, and wrote the fix back to those same bare properties, discarding the raw the comments live in — so `a { b: 1px /* c */ 0.50em; }` came out of `--fix` under `number-leading-zero` with the option `"never"` as `a { b: 1px  .50em; }`, and nothing was reported. They read and write the copy the file spells now, so every comment keeps its place, under `postcss-scss` a comment written with a double slash keeps it too, and a warning about a zero standing behind a comment points at the column the file has it in. Under `postcss-less` that raw also carries the whitespace behind an end-of-line comment, which used to go with the comment and take the semicolon of the declaration into it. One thing goes the other way, and under `postcss-scss` alone: a fraction spelled inside an end-of-line comment such a value holds is now rewritten and reported along with the rest, where only `postcss-less` used to reach it. The copy the file spells is the copy that carries such a comment, and leaving its text alone again is [#271](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/271).
	- The `linebreaks` rule no longer closes up a line break it has just reported (see [#293](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/293)). The fix deleted every carriage return of a text and then, under `windows`, wrote a pair in front of every line feed — right for a Windows pair, whose line feed carries the break through the first pass, and wrong for a carriage return standing on its own, which has no line feed behind it for the second pass to find, so both options took such a break away altogether. `a {}` and `b {}` parted by a bare carriage return came back as `a {}b {}` under `unix`, and under `postcss-scss` a value whose end-of-line comment that break closed lost the rest of its block into the comment, `--fix` reporting a clean pass on the wreck. Every break the rule reads is respelled in one pass now, a Windows pair counting as one. A form feed is still neither of the two characters this rule reads, so a file broken with one is passed over as before.
	- The `function-max-empty-lines` rule no longer writes a call nested in another a second time, over the code standing behind the outer one (see [#366](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/366)). The fix does not rewrite the value in place: it collects the text standing in front of each call it rewrites together with the rewritten call itself, moves a mark to the end of that call's own text in the source, and adds whatever stands behind that mark once the walk is over. `postcss-value-parser` walks a call before what it holds, and the text written for the outer call already carries every call nested in it, rewritten along with the rest — so by the time the walk reaches the inner one the mark already stands behind it, the text in front of it comes back empty, and the call is written a second time with everything the outer one held behind it. `a { b: f(` followed by three line breaks, `g(`, three more and `1)); }` came out of `--fix` as `f(`, one break, `g(`, one break and `1))g(`, one break and `1)); }` — a call the file spells once written twice, and a closing parenthesis with nothing to close. Plain CSS reaches this, with no comment and no custom syntax needed, and every further level of nesting adds a copy of its own. A call the fix has just rewritten is no longer walked into, since the text written for it holds what it carries already, so a nested call is collapsed along with the outer one and nothing else in the value moves. Where no fix is asked for, both calls are reported as before: each of them does hold more empty lines than the option allows. Two readings move with the fix all the same. The count of problems fixed that the `verbose` formatter prints falls to one for a whole nest of calls, that being what the fix now answers for at once. And under `reportNeedlessDisables` a `stylelint-disable` covering the inner call alone is reported as needless, the rule having nothing left to say inside it once `--fix` has answered for that call through the outer one — though the outer call's own rewrite still collapses whatever breaks stand in that range, as it did before.
	- The `named-grid-areas-alignment` rule no longer drops the parentheses and the arguments of a call standing in the value it aligns (see [#367](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/367)). The fix rebuilt the whole value out of the nodes of a `postcss-value-parser` parse, and wrote every node of it from that node's own `value` — every node but the comments and whatever carries an end-of-line comment's text, which the entry below on [#322](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/322) had already put on the file's own characters. For a call that `value` is the bare name: the arguments are the node's children and the parentheses are nowhere in it at all. So `a { grid-template-areas: "a  a" var(--x); }` came out of `--fix` as `a { grid-template-areas: "a a" var; }` — a value naming something other than what the file spells — and a call whose parentheses held whitespace of their own had that whitespace left standing outside them, `f( 1 , 2 )` coming back as a space, an `f` and another space. Plain CSS reaches this, with no comment and no custom syntax needed. Every node of the value but a row is now written back with the characters the file spells it with, whatever its type, so the rows are aligned and nothing else in the value moves.
	- The `named-grid-areas-alignment` rule no longer writes the word `undefined` into a value one of whose rows holds no cell at all (see [#368](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/368)). The rows were counted twice over — once for the comparison that raises the warning, once for the text the fix writes — and neither count agreed with the walk the fix makes over the value, nor with the other: one dropped a row spelled with nothing between its quotation marks, the other dropped a row of whitespace as well, and the walk kept both. So every row behind such a one was written one place earlier than it stands, and the last of them was handed nothing at all: `a { grid-template-areas: "" "a  a" "b b"; }` came out of `--fix` as `a { grid-template-areas: "a a" "b b" "undefined"; }` — a value naming areas the file spells nowhere — and `a { grid-template-areas: "   "; }`, in which nothing is out of line at all, came out as `a { grid-template-areas: "undefined"; }`. Plain CSS reaches this, with no comment and no custom syntax needed. Every row keeps a place of its own now, whatever it holds, so the rows are aligned where they stand and a row with no cell is written back with nothing between its quotation marks, its whitespace taken away as it is taken from the ends of any other row. Under `alignQuotes` in a declaration spanning lines it is padded to the width of the others instead, its closing quote lining up with theirs, and a warning moves either way with that: a row spelled with nothing between its quotation marks is reported now, its quote having been left out of the count altogether, and one spelled with whitespace already as wide as the rest is no longer reported, the warning it used to draw being that same miscount, which then wrote `undefined` over the row and widened every column of the grid to that word on the run after.
	- The `no-missing-end-of-source-newline` rule no longer carries off what a file ends on when it closes that file with a line break (see [#369](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/369)). The break was written in place of the root's trailing raw rather than behind it, and that raw holds everything standing behind the last block: a free semicolon, the whitespace around it, an empty line. So `a { color: pink; };;` came out of `--fix` as `a { color: pink; };` and a break, `a { color: pink; }  ;  ;  ` as `a { color: pink; }  ;` and a break, a rule the file followed with an empty line and a run of spaces lost that line as well, and a stylesheet holding nothing but two semicolons came back as a break and nothing else. Taking one of those semicolons away rescued no file, `lightningcss` refusing `a {};` exactly as it refuses `a {};;`; the rule that takes them all is `no-extra-semicolons`, as `max-empty-lines` is the one that counts empty lines and `no-eol-whitespace` the one that ends a line cleanly. The break is now written behind everything the raw holds, with a single exception: a run of spaces and tabs standing on its own behind the file's last line break comes off instead, since such a file has ended its last line already and a break written behind that run would leave it an empty line it never had.
	- The `unit-case` rule no longer recases the text of an interpolation (see [#298](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/298)). `postcss-value-parser` breaks a value at whitespace, and an interpolation holding whitespace is broken along with it, so `10px#{$a != $b}` reached the rule as the word `10px#{$a`, which is CSS on one side of the brace and Sass on the other. The guard that keeps this rule to plain CSS asks a word at a time whether it holds an interpolation, and that word holds no closing brace and so held none: the rule called `px$a` the unit of `10`, said as much in a warning no user could act on, and its fix recased the word whole. Sass tells its names apart by case, so a stylesheet that compiled stopped compiling; Less reads no interpolation holding whitespace at all, and there the fix rewrote text the compiler was going to print as it stood. The interpolations are placed in the value once now and every word measured against them, so a word carrying any of one is passed over whichever side of it the word opens on. This wants no custom syntax: plain CSS carries such a value in a custom property and in a set of media parameters, and both were recased. The rule therefore says nothing about a unit written inside an interpolation either — it used to name the `px` of `#{$m * 2px}` and recase it, and to name the `px` of `#{$m*2px}` and then write nothing at all — so whether the interpolation holds whitespace no longer decides what the rule does with the value around it.
- A warning is no longer raised over code that is already right, nor over the text of a comment taken for code:
	- The `selector-pseudo-class-parentheses-space-inside` rule no longer reports a pseudo-class it has already fixed, where the last argument holds nothing but comments (see [#128](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/128)). The whitespace in front of the closing parenthesis was not in the parsed selector at all, so the `always` options asked for a space that was already there and went on asking however many times the fix was run, reporting it at a column that fell inside the comment. `a:not(/**/)` is now fixed into `a:not( /**/ )` once, and the output is left alone from then on. A run of several spaces in front of that parenthesis is left as it is now, as one standing anywhere else inside the parentheses always was. None of this reaches a selector carrying an inline comment under `postcss-scss`, which the rule reads from a copy of itself that spells every one of those comments `/* */` and writes its fix to a copy that is never printed; the rule reads and writes both copies now, which was [#163](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/163) and is answered below.
	- The `declaration-colon-newline-after` rule no longer reads a colon of the value as a second colon of the declaration (see [#408](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/408)). The text the rule walked was meant to hold the property and the colon alone, and it ran on into the value by one character less than `raws.between` is long, so whitespace wide enough around the colon carried the walk past a colon of the value — a data URI's, an SCSS map's, a `progid:` filter's. `a { background  :        url(data:x); }` was reported twice under `always`, the second time over the `data:`, and `--fix` wrote a line break in front of the URI and did it again on every run for ever. The walk is over `raws.between` alone now, the raw PostCSS files the declaration's own colon in, so no colon of the value is read as a second one and one run of `--fix` settles the file.
	- The `function-parentheses-newline-inside` rule no longer reports an opening parenthesis that an inline comment already follows correctly (see [#141](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/141)). The `always` options let a comment stand between the parenthesis and the line break they ask for, and used to walk past a block comment while stopping at an inline one, so a function already spelled the way the option asks was reported and then reformatted by the fix.
	- The `media-feature-parentheses-space-inside` rule no longer reads a media feature out of an inline comment standing in a media query, nor writes inside such a comment (see [#138](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/138)). A parenthesis in the text of a comment used to open a feature as far as the value parser was concerned, and the fix then put the space the option asks for into that text.
	- The `selector-combinator-space-before` rule no longer reports a combinator that opens a selector when a comment stands in front of it (see [#66](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/66)). A selector list broken over several lines and interleaved with comments is now left alone instead of being pulled onto one line. 	- The `selector-combinator-space-before` and `selector-combinator-space-after` rules no longer drop the warning about whitespace they cannot write. 		- the fix now reaches the output instead of being silently discarded, and the comment keeps its `//` spelling, whatever kind of combinator the comment stands beside: one folded into the raws of a `>`, `+` or `~` used to be rewritten into a block comment by a fix made elsewhere in the selector, and the position reported there drifted two characters per comment;

		- a comment ends with its line, so a string on the next one is checked as before.
	- The `selector-pseudo-class-parentheses-space-inside` rule no longer reports an end of the parentheses that holds no argument, nor throws when fixing one (see [#127](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/127)). Less reads its keywords in lower case only — the compiler prints `.a:hover WHEN (1 = 1)` as it stands, and answers `when NOT (1 = 1)` with a syntax error — while `isStandardSyntaxSelector` matched the word in any case and passed such a selector over. Nothing valid was silenced by that, since a parenthesis opening after whitespace is nothing a CSS selector has, but what the plugin says about such a file is now what the syntax says.
	- Interpolation standing in the text of a quoted run is no longer read as interpolation of the selector (see [#170](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/170)). `isStandardSyntaxSelector` asked whether the selector holds `#{…}`, `@{…}`, `${…}`, `{{…}}` or `$(…)` before it emptied the quoted runs, so `[title="#{a}"]` was taken for a preprocessor construct and several rules (see [#151](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/151)) passed the rule over, reporting nothing and fixing nothing. A pair of braces holding anything at all counts as interpolation of the template kind, so an attribute value carrying no construct whatever went with them — `[data-config='{a:1}']` for one, whose braces are the text of a value and nothing else. The question is asked of the emptied copy now, as every other question about the text already was, while interpolation standing outside a quoted value is recognised as before: `[title="a"]#{$b}` and `a[b=#{c}][d="e"]` are the preprocessor constructs they were. A comment holding the text of one, `a /* #{$b} */ c`, is read as the comment it is, as a comment spelling any other construct already was.
	- The text of a quoted attribute value is no longer read as a Less `:extend` (see [#171](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/171)). `postcss-less` marks a rule as an extend by matching the text of its selector, quotes and all, so `[title=":extend(x)"]` carried the mark though what stands inside the quotes is an attribute value and nothing else, and several rules (see [#151](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/151)) passed such a rule over in a Less stylesheet while checking it in every other. The mark is asked of the code now, of the same copy the checks for a preprocessor construct already read, with every quoted run emptied. A real extend is passed over as before, `&:extend(.inline)` and `.a:extend(.b all)` among it, and so is `[title=":extend(x)"]:extend(.b)`, which carries one of each.
	- The text of a value is no longer read as a Less `&:extend` (see [#181](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/181)). `postcss-less` marks a declaration as an extend by matching the word against its value, quotes and all, so `b: "extend(x)"`, `content: "a:extend(y)"` and even `b: myextend(x)` carried the mark though all three are plain declarations Less compiles as they stand, and the rules that read a declaration through `isStandardSyntaxDeclaration` passed them over in a Less stylesheet while checking them in every other. The declaration's shape is the answer now: a real extend is the one whose property is `&`, which no standard declaration has, and it is passed over as before — in any case and spacing, since everything else Less answers with a syntax error is nothing to fix either. The shape is read in every syntax, where the mark stood only in Less, so the same `&:extend(.b)` pasted into a plain CSS or SCSS file is passed over now too, instead of being respelled `&: extend(.b)` as though the colon of that construct were a declaration's.
	- The `indentation` rule no longer raises the whole of a selector list by a level when one selector of it is a pseudo-class broken over several lines (see [#74](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/74)). The extra level issue [#30](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/30) asked for was granted by a presence check over the entire selector, so the `.foo,` standing beside a multi-line `:where( … )` was asked for an indent it must not have, and `--fix` rewrote a correct file into a wrong one — the trigger being nothing rarer than a second selector in the list, in plain CSS. The level is now raised by the parenthetical-depth tracking, for the lines inside the pseudo's parentheses and for them alone, whichever position of the list the pseudo stands in, so the sole-selector case of #30 keeps its extra level and every other selector of the list keeps its own.
		- One more shape moves with the discount that granted the old level: a line standing inside parentheses that other code opened, `a:has(.foo,` broken before `.bar)` for one, is measured at the rule's own level now. At the top level that level is zero either way and only the words of the warning change, `0 spaces` where `-2 spaces` was asked; inside a block the old reading expected such a line one level below the rule itself — an outdent no other line is asked for — and the line is expected level with its rule now, so a file spelled to the old expectation draws a warning it did not draw.
	- The `max-line-length` rule no longer reports the line after one that holds both an `@import` string and a `url()` argument (see [#197](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/197)). The rule took one excluded substring off a line, so the second stayed behind and came off the next line instead, with the wrong sign: a line well within the limit was reported longer by the distance to the substring it never held, while the line holding both was measured with one of them still on it. Every excluded substring standing on a line now comes off that line, a `url()` argument standing inside an `@import` string only once.
	- The `declaration-block-semicolon-*` rules no longer report a declaration that has no semicolon where a comment closes the block behind it (see [#208](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/208)). These rules pass over the declaration a block ends on without a semicolon, and found it as the block's last node; a comment standing between that declaration and the closing brace is a node of its own, the last one, so `a { color: pink /* c */ }` was measured for a semicolon the file does not hold. The `always` options of the `-before` rules wrote a break, or a space, in front of the comment and another one on every run, the file growing a line or a space at a time; `-space-after` pulled the comment up to the declaration under `always` and closed it up under `never`; `-newline-after` stepped past the comments on its own and is left as it was. The declaration is now sought past the comments, as the flag PostCSS keeps for it already reads the block, and a nested rule or at-rule closing the block is not passed over the same way, since the declaration in front of it keeps its semicolon and is measured as before.
	- The `function-comma-*` rules no longer read a comment out of an address (see [#153](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/153)). The pattern that takes the comments out of a function's arguments before its commas are measured used to read the double slash of `url(//cdn/a.png)` as one, and cut everything from there to the end of the line away with it, so the position a comma was measured at pointed at whatever stood there instead — into the middle of a word, or past the end of what was left. A comma with the whitespace its option asks for already in place was reported that way, and the fix that followed wrote where nothing was wrong: `image-set(url(//a) 1x , // c` and a line break came back from `function-comma-newline-after` with the comment moved onto a line of its own.
	- The `media-query-list-comma-*`, `media-feature-colon-space-*` and `media-feature-range-operator-space-*` rules no longer read the arguments of a function as media syntax (see [#213](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/213)). A comma, a colon or a range operator standing inside `url(x/a,b.png)`, `url(http://x)` or `url(a>=b)` was a comma of the query list, a media feature's colon or a feature's operator to the search, so a file with nothing wrong in it drew a warning, and the fix then wrote whitespace into the address, which no longer names the same resource: `@media (min-width: url(x/a,b.png))` came back as `@media (min-width: url(x/a, b.png))`. The arguments of a call are passed over now, and a media feature keeps its own parentheses: those of `(min-width: 1px)` and of `screen and (color)` open no call, since nothing is named in front of them. The search cannot be asked this of itself — it reads the character in front of the first parenthesis of a text out of nothing at all and finds a letter there, so it takes the whole of `(min-width: 1px)` for a call's arguments. A word joining two features names no call however a file spells it, so the `and(min-width: 1px)` of a file written without the space its grammar asks for is read as the feature it is, and an escaped parenthesis inside an address closes the arguments of nothing.
	- The `function-comma-*` rules no longer read one comment where the file spells two, nor a comment where a string spells its delimiters (see [#214](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/214)). The comments were taken out of a function's arguments with a regular expression before the commas were measured in what was left. It carried no `g` flag, so only the first comment ever went, and every position behind the second was off by that comment's width; and where the `*/` of one comment was followed by code, its match grew until it found a `*/` that was not, swallowing everything in between — a comma of the arguments among it. `translate(1px/*k*/, /*c*/ 2px)` was reported for a space that is there, and `translate("a/*b", "c*/ d",1px)`, where a string spells those delimiters, was read the same way: under `always` the comma that has its space drew a warning beside the one that has none, and under `never` neither of them drew anything, the position measured for the first having landed inside a word. The comments are found by reading the arguments now, in the same pass that places the commas, so `translate("a/*b", "c*/ d",1px)` lures nothing across a comma either — the comma that has its space is left alone and the one that has none is reported, and a comment code follows straight away is left where it stands, since taking it out would put the whitespace in front of it against that code.
	- Every `*-single-line` option now counts a form feed as the line break it is (see [#244](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/244)). The same reading told those options that a construct broken with one stood on a single line, so `a\f,b {}` drew `Expected single space after "," in a single-line list` although the list holds a break, and `a { color: pink;top: 0\f}` drew `Expected single space after ";" in a single-line declaration block` from `declaration-block-semicolon-space-after`. In `function-parentheses-space-inside` the fix then wrote over the break itself: `a { b: fn(\f1px\f); }` came out of `--fix` under `always-single-line` as `a { b: fn( 1px ); }`, both form feeds gone and three lines of the file made one. Such a construct is multi-line now, so the single-line options pass it over and the multi-line ones take it up.
	- The `no-eol-whitespace` rule under `ignore: ["empty-lines"]` no longer reports the whitespace standing alone on a line that a bare carriage return or a form feed opens (see [#247](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/247)). The lookback that measures such a line for emptiness reached back to the previous line feed and no further, so `a {}\r  \rb {}` drew a warning where `a {}\n  \nb {}` and `a {}\r\n  \r\nb {}` drew none. All four spellings are read alike now, and a line holding anything but whitespace is reported as before.
	- The `function-parentheses-newline-inside` rule no longer asks for a line break the function already holds (see [#246](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/246)). Whether that break was already standing was read as `includes("\n")`, while whether the function stands on more than one line is read through the three characters that end a line, so a function broken with bare carriage returns or with form feeds was multi-line to the one reading and unbroken to the other: under `always` and under `always-multi-line` alike, `a { b: fn(\r1px\r); }` was reported for the breaks it holds and `--fix` wrote a line feed in front of each of them, `a { b: fn(\n\r1px\n\r); }`, which the next run then passed over in silence. Both options read the three characters now, and a function broken on one side only draws one warning where it used to draw two: `a { b: fn(\r1px); }` is asked for the break in front of its closing parenthesis alone, and comes back `a { b: fn(\r1px\n); }` rather than broken on both sides. The break the option asks for may also stand behind an inline comment, `a { t: translate( // c\r  1px, 2px\r); }` for one, and such a value was reported and then reformatted by the fix, which wrote a break of its own in front of the comment — the shape [#141](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/141) answered where the comment is closed by a line feed. It is accepted now wherever the syntax ends the comment on the break the file spells: a carriage return under `postcss-less` and `postcss-scss` alike, and a form feed under `postcss-scss`, which ends an inline comment on one where Less does not.
	- The `function-whitespace-after` rule no longer reads a parenthesis that groups an expression as a call's (see [#230](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/230)). The parenthesis was handed to a check that looked at the character standing behind it and at nothing else, so a Less or SCSS calculation carrying a unit was a call wherever the search reached it — where the value opened on the parenthesis, and anywhere inside a call's arguments: `always` reported `h1 { width: (@a * 2)px; }` and wrote the whitespace in, which Less then compiles as two values rather than the one the author meant, and `never` closed the two values of `h1 { width: (@a * 2) px; }` up into that same expression — so whichever of the two options a project picked, one of the shapes was rewritten into the other. The rule now looks for the parenthesis a call closes instead of coming across every parenthesis there is, so a group is passed over however deeply it is nested, whether it stands inside a call or holds one, and a negated or subtracted one, `-(@a * 2)px` and `2-(1)px`, goes with it. The options of a Less import are left alone as well: `@import (reference)"foo.less";` used to draw a warning under `always` for the quotation mark behind the parenthesis, and `@import (reference) "foo.less";` used to lose that space under `never`. Plain CSS spells a group of its own inside a calculation, and it was rewritten the same way: under `never` the fix closed `a { width: calc((100% - 20px) - 1rem); }` up into `calc((100% - 20px)- 1rem)`, and under `always` it pushed `calc((100% - 20px)-1rem)` apart into `calc((100% - 20px) -1rem)` — each of them a sum the CSS grammar no longer reads, so the declaration was dropped by the browser rather than merely respaced. A second plain CSS shape is read better than before as well: an escaped parenthesis inside an address closes no call, so `a { b: url(a\)b)red; }` is reported at the parenthesis that does close the call and the fix no longer writes a space into the address, where `always` used to put it. One more parenthesis stops being read and rightly so: a run of characters opening on a digit names nothing, so `a { b: 2px(1)red; }` and `a { b: 2and(1)red; }` are a dimension in front of a parenthesis rather than a call, and the whitespace behind them is none of this rule's business.
	- The `block-closing-brace-empty-line-before` rule under `always-multi-line` no longer asks for an empty line a block already holds (see [#245](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/245)). An empty line was read as two line feeds, so `a {color: pink;\r\r}` and `a {color: pink;\f\f}` were reported although each holds one, where their line-feed twin was passed over.
	- The `function-parentheses-space-inside` and `function-parentheses-newline-inside` rules no longer report a function whose closing parenthesis a comment has swallowed, nor write outside one (see [#131](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/131)). `postcss-value-parser` knows nothing of a comment opened by a double slash, so a `/*` standing in the text of one opens a block comment to it that never closes and takes the parenthesis with it. The function comes back marked unclosed, and the stringifier prints what such a node keeps in front of its parenthesis behind it instead, so the space or the line break an `always` option asked for landed outside the function; PostCSS then trimmed it out of the value and into the raws of what followed, which left the value looking untouched to the next run, and the next run wrote another one. `--fix` grew the file by a character a run, for as long as it was asked, and reported nothing at all. Such a function is left alone now, warning and all, since the parentheses these options are about are not where the parser puts them. A closed call standing inside one is still read and fixed where it stands, and a bracket the file really leaves open never gets this far: PostCSS throws on one of those before any rule sees the declaration.
	- The `unit-case` rule no longer reads a bang flag standing in a value, or in the parameters of an at-rule, as part of the unit in front of it (see [#234](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/234)). PostCSS moves only the last `!important` of a declaration out of the value, so every flag written in front of it stays where it was, and `postcss-value-parser` reads `1px!important` as one word — whose unit the rule measured as `px!important`. Under `"upper"` the fix wrote the keyword in capitals along with the unit, so `a { b: 1px!important 2px!important; }` came out of `--fix` as `a { b: 1PX!IMPORTANT 2PX!important; }`, and nothing was reported; under `"lower"` the same reading rewrote a declaration whose units were already right, `a { b: 1px!IMPORTANT 2px!important; }` losing the spelling its flag was given. A unit ends where the flag begins now, so the keyword keeps the case the file gives it under either option, the warning names the unit rather than the unit and the flag together and ends where the unit ends, a Sass `!default` or `!global` stands the same way, and a Less at-variable such as `@variable: 10px!important` is read like any other declaration. A word whose whole unit is a flag, the `1!important` of `a { b: 1!important 1px!important; }`, carries no unit at all and is passed over. A unit no specification knows is recased as before: the rule asks where the unit ends, not whether it is one.
	- The `unit-case`, `color-hex-case`, `function-parentheses-*-inside` and `number-*` rules no longer read the text of an end-of-line comment as code (see [#271](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/271)). These six walk a value with `postcss-value-parser`, which has a node for a block comment and none for one opened by a double slash, so a block comment reached them as a node of its own and was passed over while an end-of-line comment reached them as ordinary words, calls and divs, and each worked on that text as it works on the value. `a { b: 1px // 2px` followed by `3px; }` came back from `--fix` with `// 2PX`, a hex colour written in such a comment was recased, a call spelled there had its parentheses spaced or broken, and a number written there lost a zero or gained one. A set of at-rule parameters carries such a comment the same way, and was read the same way — under `postcss-less` all along, and under `postcss-scss` since [#233](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/233) put `unit-case` on the copy the file spells and [#268](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/268) did the same for the two `number-*` rules. A node standing in that text is left alone now, and nothing is reported about it, while the code standing on either side of the comment is read and fixed as before.
		- `function-parentheses-newline-inside` did the worst of it, since the line breaks its `always` options wrote ended the comment early and turned the rest of its text into code the file is read by.
		- A call opened in the comment's text is left alone however far it reaches, parentheses and all: `a { b: f( 1 ) // g( 2` followed by `3 ); }` used to have the spacing of both its calls written, on the comment's line and on the line under it, and only the call in front of the comment is spaced now. What such a call gathered out of the code below the comment is walked as ever, so a unit, a colour, a number or a nested call standing there is read where it stands.
		- Where such a call was all a warning was ever about, the warning goes with it. `a { t: foo(1px // c) calc(` followed by `2px); }` drew warnings from both `function-parentheses-*-inside` rules about the parentheses of a `calc`, and Less itself reads that stylesheet as `foo(1px 2px)`: the whole of `calc(` stands inside the comment. The guards that hold a fix back where it would carry code into a comment — [#129](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/129), [#280](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/280) and [#281](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/281) — still stand in front of every fix that would. A call the parser closes the other way about — opened outside such a comment and closed on a parenthesis standing inside it — is left alone too, which is [#320](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/320) and is answered below.
	- The `function-parentheses-space-inside` and `function-parentheses-newline-inside` rules no longer read a call the parser closed on a parenthesis standing inside an end-of-line comment (see [#320](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/320)). `postcss-value-parser` knows nothing of such a comment and reads its text as code, so a closing parenthesis written there closes a call opened outside it: `a { b: f(1px // c) h(2px` followed by `2px); }` is one call of `f` reaching over the break to every syntax that spells the comment, and came back out of the parser as a closed `f(1px // c)` with an `h(2px` and the break and `2px)` beside it. Neither parenthesis the parser gave that `f` is one the file writes, and the whitespace an `always` option asked for in front of the second went inside the comment's text; a `never` option took away a space the comment's text held. Under `function-parentheses-newline-inside` the break written there closed the comment early and turned what stood behind it into code, so `a { t: foo(1px // c) calc(` followed by `2px); }`, which Less compiles to `foo(1px 2px)`, came out of `--fix` as two calls. Such a call is left alone now, warning and all, the way one the parser marks unclosed has been left alone since [#131](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/131), and this is the half of [#271](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/271) that stayed open — that one leaves alone a call opened inside such a comment, this one a call closed inside it. A call nested inside either is still walked and fixed where its own parentheses stand. The opening parenthesis of such a call is one the file does spell, and the warning about it goes as well: the closing one is not, so whether the option is satisfied there is a question the rule cannot put at all. A rule reading the opening half alone would write its whitespace and report the problem solved either way — rightly where that parenthesis already carries what the option asks, and over a value still violating it where it does not, at a parenthesis no run can reach. Nothing the rule can see tells the two apart.
		- One shape loses a warning it ought to keep, and loses it to a reading of its own. `postcss-scss` records a double slash as a comment only where whitespace stands in front of the pair, so for `a { transform: translate(1px, 2px// keep me` and a form feed and `); }` the plugin reads no form feed as the end of that comment and takes the parenthesis for the comment's text, though Sass ends the comment there and compiles the value to `translate(1px, 2px)`. The whitespace in front of that parenthesis is no longer reported; the fix that would have taken it away was never written either, the guard in front of it having held it back on every run. The other three — `block-opening-brace-space-before`, `block-opening-brace-newline-before` and `declaration-colon-space-before` — read a `raws.between`, and plain CSS puts no comment of that kind in one: it reads `a //c` as a selector rather than as a selector and a comment. The only double slash that can reach those three is the pair `*/` and `/*` spell between two block comments, which the reading already tells from a comment's own, so nothing they do changes. The guards themselves are as load-bearing as ever: under Sass and under Less a `//` comment does stand in a `raws.between`, and the fix is still held back there.
	- The `block-closing-brace-empty-line-before` rule's fix no longer writes a second empty line onto a block that is one break short of holding one (see [#245](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/245)). It put `context.newline` twice on the end of whatever stood there wherever the break already standing was neither a line feed nor a Windows pair, so `a {\rcolor: pink;\r}` came back as `a {\rcolor: pink;\r\n\n}` — two empty lines where one was asked for, spelled with a break the file does not use — and the next run was silent, so the file kept them. The break already standing is written twice over now, so `a {\rcolor: pink;\r}` comes back as `a {\rcolor: pink;\r\r}`; and where the whitespace holds none, the break the file ends its lines with is written instead, so `a {\rcolor: pink;}` comes back as `a {\rcolor: pink;\r\r}` as well. That break is read off the file, as [#267](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/267) has it below, and `context.newline` is written only where the file ends no line at all. The fix under `never` keeps that spelling too, writing the first break of a run in the whole run's place rather than `context.newline`, which knows a Windows pair and a line feed and no other break. A stray semicolon standing in that whitespace no longer moves the empty line either: it is written behind the semicolon rather than in front, and taken away from around it under `never`, where `a {\ncolor: pink;\n;\n}` used to draw a warning that no run of `--fix` could clear.
	- The `block-closing-brace-empty-line-before` rule's fix now spells its empty line the way the file spells its lines, wherever the break it copies stands (see [#267](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/267)). Where the whitespace in front of the closing brace held no break of its own, one was looked for in the whitespace the file keeps around the block and its tree — in front of a node, behind its name, between it and what follows that name, inside its block at the end, and in the semicolon a nested block may be followed by — and whitespace is not the only place a break stands. One standing in a selector, in a value, in a set of parameters or inside an `!important` was invisible to that reading, and `context.newline` went in instead, which reads a line feed and a Windows pair and knows neither of the two other breaks a stylesheet is written with: `a {b,\rc {color: pink;}}` and `a {color: pink !\rimportant;}` each came back carrying a line feed the file holds nowhere else. The file itself is read now, and the answer is the first break it spells outside its comments and its strings — a break inside either ends a line and says nothing about how the file ends its lines — so both come back spelled with the carriage return they are written with, and `context.newline` is left for the file that ends no line at all. A file spelling its lines two ways answers with its own first break rather than with its block's, so `a,\nb {\rcolor: pink; }` gains a line feed where it used to gain a carriage return.
	- The `function-parentheses-*-inside` rules now fix a closing parenthesis that neither reading of a line break moves into an inline comment (see [#132](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/132)). Both rules guard that fix by asking twice whether such a comment holds the parenthesis — once as the value stands, once as the fix would leave it — and each asking counted a set of breaks of its own: the first every break either syntax closes a comment on, the second only the breaks both of them do. Where a break of the difference stood between the double slash and the whitespace the fix writes over — a form feed, which Sass ends a comment on and Less does not — the two answers described two different languages: the first said the parenthesis was not inside a comment yet, the second that it would be inside one afterwards, so the problem was reported on every run and never fixed, though in either language on its own the parenthesis ends up exactly where it already stood. All four options of `function-parentheses-space-inside` reached it, and `never-multi-line` of `function-parentheses-newline-inside`. Both questions are put to one and the same reading now — the one the file's own language has, which [#333](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/333) settled, both of them still being owed where the syntax has named neither — and the fix is held back only where a reading has the parenthesis outside a comment as the value stands and inside one once the fix has run. The two separators of Unicode, which the guard used to count as breaks for one of its two askings, are read by neither: a fix here writes over whitespace and the value parser counts as space only what stands below the blank, so a separator survives the fix and can never be what carries the parenthesis into a comment.
	- The `function-parentheses-newline-inside` rule now fixes the whitespace behind an opening parenthesis where an inline comment holds the first argument already (see [#281](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/281)). The `never-multi-line` option guards that fix by asking whether such a comment would hold the argument once the whitespace is gone, and never asked whether one holds it as the value stands — the two questions the closing half of the same rule has put since [#132](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/132), of which the opening half put one. So `a { t: foo(1px // c) calc( 2px` followed by a line break and `); }` under `postcss-less`, where the comment runs to that break and holds `2px` inside it before the fix as after it, was reported on every run and never written. Both questions are put now, and both of them to the reading the file's own language has, which [#333](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/333) settled, so the fix is held back only where that reading has the argument outside a comment as the value stands and inside one once the fix has run. The one question also read a text that was neither of the two wherever the fix empties whitespace on both sides of a block comment, and let a breaking fix through there: `a { t: foo(1px // c) calc(` followed by a line break, `/*b*/ 2px); }`, came back as `a { t: foo(1px // c) calc(/*b*/2px); }` — the break that closed the comment gone, and everything behind the double slash commented out. That one is reported and left alone now: emptying the whitespace there would satisfy the option only by commenting the rest of the value out.
	- The `function-parentheses-newline-inside` rule now fixes the whitespace in front of a closing parenthesis where a block comment standing there holds a line break (see [#312](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/312)). The guard on that fix asks what the value would read as once the whitespace is gone, and it used to take out every character JavaScript calls whitespace between the last thing the call holds and the parenthesis — the breaks written inside a block comment's own text among them, which no fix goes near. Taking one of those out closes the comment early and leaves the rest of the value exposed to whatever stands in front of it, so `a { t: 1px //c` followed by a form feed, `f(/*x`, a line break, `y*/`, a line break and `); }` under `postcss-scss` was reported on every run and never written, though the parenthesis stands outside every comment under both readings of a line break, before the fix as after it. The guard takes out exactly the stretches the fix empties now.
	- The `function-comma-*` rules now write the whitespace standing beside a comma wherever the parser filed it (see [#349](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/349)). These four named that whitespace by the comma's own `before` and `after`, while `postcss-value-parser` hands a run to whichever neighbour will hold it — the run between two dividers goes to the `after` of the one in front, the run between the opening parenthesis and a comma that opens the arguments goes to the function's `before`, and the run between a comma that closes them and the closing parenthesis to the function's `after`. The first of those is no comma's alone: a slash and a colon carry the whitespace of the comma behind them as readily as another comma does. The span each fix wrote was therefore empty and stood beside that text rather than over it, and it went two ways. Under `never` and `never-single-line` nothing was written at all, so `a { b: f(a, ,c); }` was reported by `function-comma-space-before` at 1:13 and came back from every run of `--fix` exactly as it went in, and `never-multi-line` went the same way wherever a break stood in that run instead. Under `always` and `always-single-line` the character was written at the comma, behind the run instead of over it: `a { b: f(a,\t\t,c); }` grew a space on every run under the two `*-space-*` rules and never satisfied the option it was asked for, while the two `*-newline-*` rules wrote their break beside the run and settled there, leaving whitespace their option tolerates rather than the whitespace the file was asked for. Both are fixed, and the four positions are read the same way, so a comma behind another comma, one behind a divider of any other kind, one opening the arguments and one closing them are all written like any comma between two words: `a { b: f(1 / ,2); }` under `never` now comes back as `a { b: f(1 /,2); }`, where it used to come back untouched. A file with no such comma in it is written exactly as before, and so is one where an end-of-line comment stands in front of that run, the break which closes the comment being the run itself: the guard that holds a fix back from writing inside such a comment is asked as it always was, and every warning it holds back still stands. The whitespace between an opening parenthesis and a comma is also what `function-parentheses-space-inside` writes, so asking that rule for a space there and one of these for none cannot be satisfied by any file: `a { b: f( ,a); }` settles with one of the two warnings standing, and which one depends on the order the rules are listed in, the one written last having the final say. That is the standing [#166](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/166) leaves between `value-list-comma-space-before` and `declaration-colon-space-after`, order and all. The other way about is satisfiable, since a comma that opens the arguments is asked for nothing by `always`: `a { b: f(,a); }` answers both rules at once. Nothing runs away with either — a second `--fix` writes the same file as the first.
	- The `no-missing-end-of-source-newline` rule's fix now spells the break it writes the way the file spells its lines (see [#282](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/282)). It wrote `context.newline`, which Stylelint reads out of the file as a line feed with an optional carriage return in front of it and falls back to the line ending of the machine for, so a file broken with bare carriage returns or with form feeds was closed with a character it holds nowhere else. The break is read off the stylesheet itself now, outside its comments and its strings, and `context.newline` is left for the one that ends no line at all — a stylesheet written on a single line, or one whose only breaks stand inside a comment or a string.
		- The break read off a Less file may be a form feed standing inside a `//` comment or inside an unquoted address, which Less reads as the text it stands in and refuses to read anywhere else; closing the file with one leaves a file Less will not compile. The reading is older than this change and shared — `block-closing-brace-empty-line-before` spells its empty line with the same character on the same file — and this rule is the second place it is reached from (see [#373](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/373)).
	- The `declaration-bang-space-*` rules now write the whitespace standing beside a bang wherever the parser filed it (see [#289](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/289)). These two named that whitespace by the one text of the declaration the bang stands in, while PostCSS prints a declaration from four — the property, what stands between it and the value, the value itself, and the raw of the flag — and leaves the run beside a bang in whichever of the last three the shape of the value gives it to. The run in front of a bang reaches the flag's raw only where the value has a word of its own to leave behind: `a { b: /*c*/\t!important; }` keeps it at the tail of the value, `a { b:  !important; }` has nothing else in the value at all, and `a { b: /*c*/\t!default; }`, whose flag PostCSS never parts from the value, keeps it at the tail of what stands between the property and the value. The run behind a bang goes the other way in `a { b: x!  !important; }`, where the bang closes the value and the run opens the flag's raw. On all four the span each fix wrote stood beside the run rather than over it, and it went two ways. Under `always` the character was written against the bang and the run left standing, so `a { b: /*c*/\t!important; }` grew a space on every run of `--fix` and never came to satisfy the option it was asked for. Under `never` nothing was written at all, so the same declaration came back from every run exactly as it went in. Both ran clean either way, since Stylelint counts a problem fixed once the fix callback has been called, whatever that callback wrote — the warning was there to be read only with `--fix` off. Both are fixed: the run is measured and written in the declaration as the file prints it, and an edit reaching across two of those texts empties the run in each of them and writes the space the option asks for against the bang. A declaration whose run the parser filed with its bang is written exactly as before, and so is one where an end-of-line comment stands in front of that run — the guard that holds `declaration-bang-space-before` back from writing inside such a comment is asked as it always was, and every warning it holds back still stands. Nothing runs away either way now: a second `--fix` writes the same file as the first.
	- The `unit-case` rule now underlines the unit a warning names rather than the word that unit stands in (see [#296](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/296)). The unit is read out of a copy of the word with the characters an interpolation is spelled with taken out of it and the `\0` and `\9` hacks with them, while the warning ended where the word ends, so whatever those cuts took off was underlined along with the unit: under `upper`, `a { b: 10px\0; }` was reported over `px\0`. The parts of a multiplication were worse off. Each was handed a node built on the spot, opening at the part's place inside the word with the part's own length and one more added on top, and closing where the whole word closes, so the two positions described no text of the part at all: under `lower`, `a { b: 2*10PX; }` was reported past the end of its only line, and `a { b: 10px*2REM; }` over the closing brace of the block, its two positions running backwards until PostCSS clamped them to that one character. Both positions are counted off the unit inside the node now, and every part of a multiplication carries the positions the file gives it. Where a cut falls inside the unit rather than beside it, the run underlined is the text that reading was taken from: `10P\9X`, whose unit is read as `PX`, is underlined from its `P` to its `X`, and `10px#fff`, whose unit is read as `pxfff`, from its `p` to the last `f`.
	- Every guard that asks whether a fix would write inside an inline comment now reads the line breaks the file's own language reads (see [#333](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/333)). Sass ends such a comment on a form feed, on a line feed and on a carriage return alike; Less normalises the line endings of a file before parsing it and reads no line in a form feed at all. The scan behind every one of those guards closed a comment on a line feed and on a carriage return and on nothing else, which is Less's reading entire — and handed it to every caller whatever the file was written in, so that every stylesheet was read as a Less stylesheet. So under `postcss-scss` a fix standing behind a form feed was refused wherever Sass had already closed the comment on it: `a { b: 1px // c` and a form feed and a tab and `2px; }` under `declaration-block-semicolon-space-before` with `always` was reported on every run and never written, and the warning survived every run of `--fix` over a stylesheet no fix could damage. The syntax itself is asked now which breaks it reads a line in, by one parse of a probe kept against that syntax, and the answer travels with the question: `block-closing-brace-space-before`, `block-closing-brace-newline-before` and `declaration-block-semicolon-space-before` write behind such a form feed under Sass, and the two `function-parentheses-*-inside` rules, which used to put every question under both readings whatever the file was written in, put it under the one the file has. Under `postcss-less` every one of those fixes is refused exactly as before, the comment running past the form feed to the end of its line, and not a byte of any Less file changes. Where the syntax has said nothing about the character — a host language that finds no stylesheet in the probe, one that cannot parse it at all — both readings are owed rather than Less's alone, and a fix that either of them would carry into a comment is held back: for the two `function-parentheses-*-inside` rules that is what they already did, and for the other nine callers of the guard it is a refusal they did not use to make.
	- The `at-rule-semicolon-*`, `block-closing-brace-*`, `block-opening-brace-*`, `declaration-block-semicolon-*`, `declaration-block-trailing-semicolon`, `indentation` and `no-extra-semicolons` rules now measure a node in the copy of it the file spells (see [#139](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/139)). These rules find the brace, the semicolon or the indent they report by the length of what a node prints, and `Node.toString()` goes through PostCSS's own stringifier rather than the one the file was opened with. The two part company in five places: `postcss-scss` keeps a second copy of a value, of a set of parameters and of a selector, and PostCSS prints the copy whose `//` comments the syntax has rewritten into block comments, two characters wider for each of them; both custom syntaxes print a comment opened by a double slash as a block comment, two characters wider again; `postcss-less` holds a mixin call as an at-rule whose leading dot stands in a raw; the `!important` of such a call PostCSS does not print at all; and a Sass nested property is a declaration carrying a block, which `postcss-scss` prints and PostCSS's own stringifier drops. The index a warning carries is counted in the text of the file, so a position measured in that printed copy stood as far past its mark as the two copies differ, and where those characters ran past the end of a line the warning was reported on a line the file does not spell it on. Where an option turns on a block being single-line or multi-line, the same characters changed which of the two the block was taken for rather than the column it was reported at. A media query whose feature carries such a comment and whose block is written on one line was measured as multi-line, so every option about a multi-line block was put to it and every option about a single-line one passed it over. Over that one file and every primary option of the nine `block-*` rules, eleven warnings go and six arrive. Every one of these positions is measured in the node as the file spells it now, and the block a rule asks about is the block the file spells. Where a rule counts on past the end of a node — the two `declaration-block-semicolon-*-after` rules step over the semicolon that way — it still counts a character at a time, so a semicolon the file does not write against the node is reached only where nothing stands in between. The Less half of [#374](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/374) goes with it, a block ending in a mixin call no longer being measured as though the call were an at-rule with no flag behind it, while the run-away rewriting that issue is mostly about is untouched and stays open.

- One run of `--fix` now does the work that run's own writing uncovers, instead of leaving it for the next one:
	- The `function-parentheses-newline-inside` rule now reads a value against the inline comments it holds once the fixes collected so far are written into it (see [#288](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/288)). The spans such comments occupy were found once per declaration, before the value was walked, and a call opening inside one of them is passed over — its parentheses are the text of a comment rather than parentheses of the value. The `always` and `always-multi-line` options write line breaks, though, and a line break is what closes a comment opened by a double slash. So in `a { t: foo(1px // c) calc(/*b*/`, a line break, ` ,2px`, a line break, `); }`, where the comment runs from the double slash past `calc(` to the first break of the value, the break the fix writes in front of the closing parenthesis of `foo` closes that comment early and leaves `calc(` standing in code with its own break still missing. The rule went on reading the value against spans it no longer had, said nothing about `calc(`, and handed back a file one break short of what the option asks for; a second run of `--fix` wrote that break and a third settled, so nothing ran away. The spans are found again now, wherever a fix has been written and before the next call is read, and the one run writes both breaks. A run without `--fix` is unchanged, and writes nothing: as the file stands, `calc(` is the text of a comment.

- A walk over a run of comments now costs a step per comment rather than a stack frame:
	- The `at-rule-semicolon-newline-after`, `declaration-block-semicolon-newline-after` and `declaration-block-trailing-semicolon` rules now read a stylesheet holding a long run of comments (see [#360](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/360)) ([@chiliec](https://github.com/chiliec)). All three step over such a run through one walk — from a node's own sibling in the first two, from the front of a block in the third — and that walk called itself once per comment, so a long enough run ended the whole run in `RangeError: Maximum call stack size exceeded` and no file was reported on at all; around eleven thousand comments is the threshold on Node 26, and twenty thousand throws every time. A comment costs that walk a step now rather than a stack frame, so a stylesheet is read whatever run of comments it holds. Every answer the walk gives is the answer it gave before, so nothing else about the three rules moves. The same walk had been copied into `block-opening-brace-newline-after`, which had a write of its own to make and reached this one through no caller; that copy is folded back into this walk below.
	- The `block-opening-brace-newline-after` rule now reads a stylesheet holding a long run of comments at the head of a block (see [#409](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/409)). It kept a copy of that walk rather than calling it, because it has a write of its own to make on every comment it steps over: the line break standing in front of a comment is carried onto the node behind it, so that a comment at the head of a block may hold the break the option asks for. The copy went on calling itself once per comment after the walk it was copied from stopped doing so, and it fell sooner than that walk did — eight thousand comments throws every time on Node 26, where the walk above took around eleven thousand. The copy is gone: the walk above takes that write as a callback of its own, so one walk steps over a run of comments for every rule that asks, and the next fix to it reaches all four at once. Every answer the rule gives is the answer it gave before, measured over 75 456 runs on either side of the change — runs of up to three comments, block and inline, under up to seven spellings of the whitespace standing around them, in a rule and in a nested at-rule, in a block ending in a declaration, in a comment and in nothing at all, under all three options, three syntaxes and both settings of `--fix` — byte-identical throughout. A block holding nothing but comments still comes out of `--fix` rewritten and reported on not at all, which is older than this change and filed as [#410](https://github.com/stylelint-stylistic/stylelint-stylistic/issues/410).

- Fixed removing the starting indentation along with the blank line in the `no-empty-first-rule` rule ([#47](https://github.com/stylelint-stylistic/stylelint-stylistic/pull/47)) ([@net-solution](https://github.com/net-solution)).
